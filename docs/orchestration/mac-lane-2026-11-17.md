# The Mac lane, handed to a Mac orchestrator (2026-11-17)

Written by the Claude Code orchestrator on the owner's request: "provide a whole set of tasks that the mac
orchestrator can take over and distribute to the mac executor". It replaces section 5 of
[remaining-work-2026-11-16.md](remaining-work-2026-11-16.md) as the Mac lane's list; that file's analysis and
owner decisions still apply.

## 1. Roles

**The Mac orchestrator** (new) runs the Mac lane:
- writes each packet from section 4 into `docs/orchestration/tasks/<id>.md` before it is released (one concern,
  about 2-4 h; the packet-size rule of 2026-11-12);
- releases packets to the Mac executor, one at a time per worktree;
- reviews the executor's reports and writes `docs/orchestration/reviews/<date>-<id>-review.md` (ACCEPTED,
  CHANGES REQUESTED, or a fix round);
- keeps the lane's state in `docs/orchestration/mac-lane.md` (create it; one line per packet: status, head, CI,
  review).

**The Claude Code orchestrator** (Windows PC) keeps:
- landing: every accepted packet goes into a stacked candidate (`refs/candidates/*`), gets this PC's changed
  lanes and GPU tests and the Mac's full game-file run, then lands through `tools/orch/land.py`. Main is
  protected; nobody else pushes `main`;
- `docs/orchestration/STATUS.md` and the open-question number register;
- cross-lane decisions and the owner's decisions (they go to the owner, never to an executor).

**The Mac executor** does the work of each packet and the GATE-RUNs.

## 2. How the two orchestrators work together

- **Branch for the Mac orchestrator's files:** `orch/mac-lane`, from `origin/orch/board-next`. Commit there only
  `docs/orchestration/mac-lane.md`, `docs/orchestration/tasks/*.md` of this lane and
  `docs/orchestration/reviews/*` of this lane. Never edit `STATUS.md`, `TASKS.md` or another lane's files. The
  Claude orchestrator merges `orch/mac-lane` into `orch/board-next`.
- **Accepted means:** CI green on the exact reviewed head, plus the Mac orchestrator's review. Then report to the
  owner (or by the owner to the Claude orchestrator): packet, head, CI run id, review file. The Claude orchestrator
  stacks it.
- **Open-question numbers:** the Mac lane owns **OQ-800 to OQ-899**. Use them in order; record each in
  `mac-lane.md`. Other lanes take numbers from 764 upward, so there is no clash.
- **Quiet slots:** the Mac is a separate machine, so there are none to coordinate, except that a GATE-RUN on a
  candidate comes before any other Mac job of the same day.
- **Owner decisions:** if a packet needs one, stop the packet at that point and put the question to the owner
  with options and a recommendation. Quote the owner's words in the review when he answers.

## 3. Rules every packet carries (unchanged)

- `CLAUDE.md` (evidence only, determinism first, no hardcoded limits, explicit serialization, faithful core
  separate from `rules` options), `docs/testing/evidence-contract.md`, TASKS.md §1.
- No original game pixels, frames, script text or data tables in git (generators in `tools/` write to `cache/`).
  Hashes and counts of our own results are fine.
- **No host paths in committed files:** evidence uses repo-relative paths (`build/release/...`, `cache/...`), never
  `/Users/<name>/...`. GitHub is public.
- **Committed evidence stays small:** summaries, findings, commands and SHA-256 of the raw logs; raw per-case
  outcome files stay in `cache/` (about 1 MiB per packet at most, unless the review agrees otherwise).
- Never force-push, never push `main`, no reviewer subagents in the executor, a "Decisions and reasoning" list in
  every report, NOT_RUN stated plainly.
- State changes (`kStateHashVersion`, section base versions per `docs/sim/state.md` §9.7) list every moved pin and
  golden with its reason; they land only after a full game-file run.
