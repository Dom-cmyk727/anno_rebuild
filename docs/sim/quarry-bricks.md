### HIGHMAP tables (type +0x234; P byte compare)
All four quarry types have the identical 48-byte table (2h x 2w = 8 rows x 6 columns for 3x4). Every mine type 1203, 1205, 1210, 1206, 1212, 1214, 1216, 1217 has one identical table. The quarry's differs from the mines' in exactly two bytes (indices 20 and 21: row 3, columns 2 and 3): 0x20 in the mines, 0xff in the quarries. Rows (quarry / mine differs only in row 3):
```
ff ff ff ff ff ff   (x3 rows)   row3 quarry: ff ff ff ff ff ff   mine: ff ff 20 20 ff ff
row4: ff ff 10 10 ff ff   row5: ff ff 10 10 10 10   row6: ff 10 0c 0c 10 10   row7: ff ff 04 04 ff ff
```
So the quarry's terrain test (AnnoGame 0x10008a80, rule in `tools/mine_terrain_ref.py`) is the mine's with one row-3 pair of cells never refusing (0xff): marginally more permissive. This is placement only (settled in OQ-554).

## F1 Which quarry does the worker pick (D)
- The step-A start 0x10059bf0 only COLLECTS: rect query (mask 8, callback 0x1005a500 pushes every building with `home.slot+0xd4(b) > 0`; list order of the BuildingIndex list is irrelevant, nothing is chosen there). It then registers each candidate's goal points (`cand.slot+0xf8(figure type, 0, searcher)`, 0x10059d0f-0x10059d4b), sets `searcher.slot+0x7c(callback 0x1005a400, &ctx)` and runs the walk search `fig.slot+0xcc(0, 4, searcher)` (0x10059d8c-0x10059d95).
- ctx (stack block at esp+0x34 before the push, 0x10059d67-0x10059d7c): `+4 = 0` (threshold), `+8` = island Y, `+0xc` = city, `+0x10` = the home, `+0x14` = chosen building (starts 0).
- The choosing callback is **0x1005a400**, the SAME callback the workshop carrier job (0x33) uses (src/sim/src/transport.cpp:541 "The callback 0x1005a400"). For each popped goal node: node x,y -> tile (`searcher.slot+0x98/+0x9c`, `_ftol` 0x1005a41a/0x1005a42c) -> island slot +0x170 -> BuildingIndex point lookup (mask 0xa) -> `score = home.slot+0xd4(building, &goods)`; if `score <= searcher.slot+0x8c` (best so far, initial 0, transport.cpp:498 "best score starts at 0 for every search, 0x10003dbf") the node is skipped; else `searcher.slot+0x90(node,4)` (selected), `slot+0x88(score)`, `ctx.building = b`, then `if (ctx+4 > b.slot+0xa4(goods)) continue else searcher.slot+0xb0() (STOP)` (0x1005a4a3-0x1005a4e2). Here ctx+4 = 0 and the quarry's stock is 0x100, so the first qualifying goal node STOPS the search. (The carrier job sets ctx+4 = 3/4 of its capacity; that is the only difference to the carrier.)
- Therefore: the winner is the first qualifying goal node popped by the engine's frontier (lowest accumulated u16 cost, FIFO among equals: docs/sim/state.md 5.9 clauses 5 and 7, the same rule as the forester's step A). That is the path-nearest reachable quarry entrance, not Euclidean, not list order, and unreachable quarries lose. A building scored at its first reached entrance only matters once (further entrances of the same building add nothing).
- PRNG: none. The calls in 0x10059bf0, 0x1005a400, 0x1005a500, 0x100708b0, 0x100553e0, 0x10055420 and 0x10057ae0 are only `_ftol` (0x100b5f90), the helper 0x100543b0 and virtual calls; no `rand`, no world-PRNG slot.
- Existing adaptation that matches: `choose_source` (src/sim/src/transport.cpp:386-600, the `visit_carrier` lambda at 541-551, `workshop_offer` 346, `workshop_priority` 285, `search_area` 253, candidates mapped to goals 484-500). Deltas to implement: (a) collector mask 8 not `kCarrierMask` 0xa (transport.cpp:30; the mason's push is `push 8` at 0x10059ccf; the callback's point lookup still uses 0xa), (b) threshold q = 0 so `keep_going` is false (Stop at the first scored hit) instead of 3/4 capacity (transport.cpp:566), (c) the home's priority for a Farm payload (see F4; `workshop_priority` returns -1 for non-Workshop/Inn payloads, transport.cpp:314-316), (d) `available()` returns 256 for a Quarry-class building (today `has_output_store` is false -> 0, transport.cpp:279-283), (e) the start is the FIGURE's position (it spawns at the home's first entrance, driver.cpp:198-204) as in harvest.cpp:245, not all home entrances (transport.cpp:484); for a figure standing on the first entrance point the difference is only the other entrances of the home.

## F5 Placement difference (T: tools/mine_terrain_ref.py section 11; reference run)
- Rule: a site is refused as soon as `table[k] <= floor(h_k) - (lo & 0xff)` for any cell (unsigned table byte, signed difference), plus the inherited `lo >= 32`. So a table byte B means "the terrain at that sample point may rise at most B-1 height units above `lo`": 0x20 = at most 31, 0x10 = 15, 0x0c = 11, 0x04 = 3; **0xff = unconstrained** (the difference is at most 255-32 = 223 < 255, so it can never refuse).
- The quarry table replaces the mine's 0x20 at indices 20, 21 (row 3, columns 2 and 3) by 0xff. Those two cells sample (rot 0) the quarter points (5,7) and (7,7), i.e. inside tile (1,1) at fractions (1,3) and (3,3): heights `(b + 3c)/4` and `(2d + b + c)/4` of that tile's vertices a=(1,1) b=(2,1) c=(1,2) d=(2,2). Other rotations: (7,7),(7,5) in tile (1,1); (7,9),(5,9) in tile (1,2); (9,5),(9,7) in tile (2,1).
- So the quarry accepts exactly the mine's accepted sites PLUS sites where only these two sample heights are >= lo + 32 (every other cell, 0x10/0x0c/0x04 and the lo >= 32 rule, still applies). It is a strict superset of the mine's acceptance (the quarry never refuses where the mine accepts).
- Reference check (T, 3x4, all vertices 0x20 so lo = 0x20, then one vertex 0xA0): rot 0 vertex (x=2,z=1): mine refuses, quarry accepts; rot 1 (1,2); rot 2 (1,3); rot 3 (3,1): each mine False / quarry True (all other single-vertex raises agree between the two tables). A quarry therefore may sit where a mountain top vertex pokes 32+ above the lowest cell at that one tile. This is placement only; nothing at run time depends on it (the "any mountain" rule of OQ-554 is the HIGHMAP test plus lo >= 32 (inherited), no deposit). The two tables were compared byte by byte (P); the reference run (not the original bytes via unicorn) gives the vectors above.
