## Facts
- **D** `JAGDHAUS` (PRODTYPE 5, type 805) has its own runtime class; its tick is `0x10069f40` (gate `(u16)(t - [esi+0xa]) >= 0x1f4` = 500, `0x10069f5d`; `last += 500` at `0x10069f68`). `types.cpp` maps it to `TickKind::None`; the building is inert in the sim.
- **P** Type 805: 3x3, radius 8, input `FLEISCHTIER` (goods 137), outputs `NAHRUNG` (26) and `TIERHAEUTE` (18), per step in 57 -> out 43 / 26 (8.8), capacity 1024/1024, time 768/1280 /128, max figures 1, figure type 108 (ROUTETYPE index 12, layer 2, capacity 256). The fur trapper 824 (`PELZJAEGER`, `PELZTIER` -> `PELZE`) sends the **same figure type 108 / route 12**; the engine's `FurTrapper` tick is ported but never sends (no target: `driver.cpp`, O-25).
- **D** (shape only) `0x10069f40` after the gate: returns when both line bytes `[+0x28]`/`[+0x29]` are 0; decays the activity words `[+0x20]`/`[+0x22]` by `x*127>>7`; returns when flag bits 4/5 of `[+0xc]` are set; computes a rate `bl` from the raw store `[+0x24]` (u16) and the type property pair `0x44f`; produces into `[+0x18]`/`[+0x1a]` with the line shares `[+0x2a]` and `128 - [+0x2a]`; updates the blocked flag bit 3; at the end, when `[+0x2c]` (workers out) is 0 and a raw-stock test passes (`0x180 / type slot +0xe0` against `[+0x24] / slot +0xe4`), asks `0x10071da0(8)` for a target and creates a figure with job `0xd` through the building's slot `+0x118`. **Not decoded:** the exact production arithmetic, which unit the raw store counts, the figure creation arguments.
- **D** `0x10071da0(8)` is the radius search "nearest animal of the input goods" (`docs/re/production.md` section 4.2a); body **U**.
- **P** The scenario islands carry a `HIRSCH` record (the string at `0x100dcf24` in AnnoWelt; island templates `.scp` have none): 668 records in the 50 `.sze`, 111,352 bytes = 13,919 entries of 8 bytes; per island 15 .. 1,570 entries, many scenario islands 0 (`cache/map-needs2/N0/n0_scenes.txt`).
- **D** The reader around `0x100946c0` (loads `HIRSCH`, count = size >> 3) creates one 16-byte object per entry (vtable `0x100cac04`, init `0x1007bd50`), puts it in the island's 8x8 cell grid (`[ebp+0x94]`, row stride `[ebp+0x8c]`), fills `[obj+8]` (cell column/row bits), `[obj+9]` (a type byte: from the entry or a draw of the world generator `[ebp+0x20]` slot `+0xb4` masked `& 0x1f` plus a base) and `[obj+0xe]`. These are **map objects of the island, not figures**.
- **Documented** (`docs/sim/state.md` section 12, O-12, O-25): wildlife objects and their "fauna sweep" (`WildlifeSweep`) are unported; the sim creates no animals.
- **P** Figure types 501-505 and 514-517 have ROUTETYPE index 62 (layer 4), 506-509 route 46 (layer 2): candidates for animal figures; their relation to `HIRSCH` objects is **U**.

## N1 hunting reads (2026-11-05, second pass)
Answers to the questions above, with evidence:
1. **The quarry is a figure type, named by data (P, D).** `FigurenHeader.dat` carries, for the wild animals, `ROUTETYPE "HIRSCH"` (route index 62 in the engine's name table) and a `WARE` record naming the goods the animal yields: `FLEISCHTIER` for the entries 117-120, 122-125, 127, 132, 137, 141, 501, 504, 505 (15 entries, the 15 string occurrences in the file), `PELZTIER` for 126, 129, 514, 516, 517 (and `RAUBTIER` entries 131, 529, 530 with other goods), no `WARE` for the harmless ones (121, 128, 130, 135, 502, 503, 515, 527, 528, 531, 1206). The loader `AnnoGame 0x1000fe00` resolves that name against the 0x8f goods names (`0x100103d2`-`0x10010434`) and stores the goods index at figure type `+0x100` (`0x1001044a`); type slot `+0x80` = `0x1000fc90` returns it.
2. **The target search `0x10071da0(8)` (D).** It builds a circle from the building (centre from footprint and rotation, radius from type `+0x78`), asks the island's figure manager (city `+0x10` -> `+0x18` -> `+0x18` -> `+0xa0`, slot `+0x14`) for up to 512 figures inside it (pairs of pointer and float distance, `0x200` buffer), keeps the **nearest** (strict float `<`, start 1e18) whose figure type's goods byte (`obj +0x78() -> +0x80()`) equals the building's **input goods 0**, and returns it (null when none). No ownership, kind or state test is visible there. Float distances: the same x87 float arithmetic caveat as the other searches (OQ-162).
3. **Hunter job `0xd` (D, structure).** The job switch `0x1003b0e0` sends job `0xd` to case `0x1003b1cc`: object size `0x78`, constructor `0x1005c610`, main vtable `0x100c6f90` (run `0x1005b6c0`, arrival `0x1005c570`, abort `0x1005b740`, as the harvest job) with four step objects and the shared walk-home step: step vtables `0x100c7060` (start `0x10057690`), `0x100c7038` (start `0x10054c90`, arrival `0x10054ce0`), `0x100c7010` (start `0x10056b10`), `0x100c6fe8` (start `0x10054760`, arrival `0x100547e0`) and `0x100c4640` (walk home, `0x10057ae0`). **Not yet decoded:** what each step does (walk to the animal, the kill, the carry, the credit to the hunter's two output stores, the animal's removal).
4. **Both senders share job 0xd (D).** The fur trapper tick `0x1006e5d0` and the hunter tick `0x10069f40` both call the building's slot `+0x118` with job `0xd`; the job factory is `0x1003b0e0` (byte table `0x1003b480`, index = job - 0xd, case `0x1003b1cc`), so the body is shared. **The hunter's tick (D, shape)** ends by sending job `0xd` only with a target from (2); the figure type sent is the building's figure type 0 (108, route 12).
5. **Animals exist from load (P).** The island `HIRSCH` record (8-byte entries) is read by the island loader around `0x100946c0`; it is the only place found that makes animals at scenario load. The 16-byte object it builds is **not** yet connected to a figure of the types in 1. Whether the animals then wander (their route `HIRSCH` = job 62 = `0x3e`; the job switch has no case for `0x3e`, so the figure body is something else), respawn or only exist is **U**.

## N1 hunting reads A-C (2026-11-06, third pass)
**A. The job 0xd steps (D, structure and the kill).** The five steps of the job object (`0x1005c610`): `0x100c7060` start `0x10057690` and `0x100c7038` start `0x10054c90` (arrival `0x10054ce0`) pursue the target: each step stores the target figure's **u16 id** (step `+4` / `+0xc`) and re-fetches the figure from the world's unit manager (`world +0x114`, `vtable slot +8(id)`) on every call; they drive the figure through its movement slots `+0xe8`/`+0xd0`/`+0xc8`/`+0xcc` (approach and follow of a moving target; the semantics of those movement slots are not decoded here). `0x100c7010` start `0x10056b10` plans a walk to the target's current float position (`target +0x54`, `+0x5c`) with the searcher callback `0x10054240`, but only while the target's flag word `+0x8c(0)` has **bit 1** (value 2) set. The last step `0x100c6fe8`, arrival `0x100547e0`: fetch the target by id; absent -> end; target flags `+0x8c(0)`: **bit 2 (value 4) set -> the step fails (answer 0)**; **bit 1 (value 2) clear -> nothing to take, answer 1**; else (bit 1 set): `capacity = target.type +0x84()` (the animal's figure-type capacity, `LOGIC[0x11] << 8`, `AnnoGame 0x1000fb50`), **remove the target from the manager (`manager slot +4(target, 1)`, the animal is destroyed)** and **add `capacity` to the hunter figure's cargo** (`cargo = figure +0x84(0)`, `cargo +0xc(amount)`); the shared walk-home step (`0x100c4640`) then hands the cargo to the home (`home +0xc0`, the hunter class's raw store `[+0x24]`). So **the meat is the killed animal's type capacity** (data: FigurenHeader), not a fixed constant, and **the kill is the animal's removal**; whether the hit is instantaneous or needs the animal to be in a particular state is the meaning of the two flag bits (U).
**B. Where the animals come from (D, structure).** The island sweep `0x10093480` (frame `sub esp, 0x120`) runs per chunk: it places 16-byte spawn objects (vtable `0x100cac04`, the same shape as the `HIRSCH` loader's) into the chunk's 8 x 8 cells choosing cells by **world draws** (`call [edx+0xb4]` at `0x1009366f`, `draw % n`), and then, for cells whose terrain type passes the tests (`type +0xac(0) == 0x46` or `type +0x5c() == 0x145`), creates an animal figure through `0x10092ca0(chunk, cell, type, ...)`, which places a figure by the manager's creation slot (`slot +0xa0` with float x/y). The `HIRSCH` record (`0x100946c0`) fills the same kind of object at load. So **wildlife exists because a periodic world sweep creates it with PRNG draws**, from the island records and the terrain.
**C. The animals' own tick (U).** Route `HIRSCH` is index 62; the job switch has no case for it, so the figure body is a different class; not read.
**Consequence (stop condition of the assignment).** A faithful hunting chain needs (1) the island fauna sweep `0x10093480` and its cadence (`SweepState.fauna_x/fauna_y`, `docs/sim/state.md`), which **draws from the world PRNG** and so **changes the draw order of every world with wildlife**; (2) the creation helper `0x10092ca0` and its terrain conditions; (3) the animals' tick (movement, the two flag bits). That is a wildlife lifecycle, not a reusable piece of the existing farm/forestry code, and is exactly the case the packet reserves ("wildlife lifecycle, draw-order change or unapproved gameplay adaptation"). Exact questions for the owner: (a) is porting the fauna sweep (with its draws) in scope for MAP-NEEDS-2, or is hunting to be reported PARTIAL; (b) if in scope, which function bodies must be read first: `0x10093480` (selection and cadence), `0x10092ca0` (creation), the animal class vtable behind route 62.

## Isolation of the wildlife dependency (decision 2026-11-06: not ported, hunting reported PARTIAL)
**Dependency list (everything a faithful hunting chain needs that the sim does not have; none of it is implemented, none will be invented):**
1. `0x10093480` the island fauna sweep (per chunk, periodic; cadence state `SweepState.fauna_x/fauna_y`, `docs/sim/state.md`): which cells, when, how many animals.
2. Its draws: world PRNG `slot +0xb4` at `0x1009366f` (`draw % n`). Porting it changes the draw order of every world with wildlife: an owner decision on scope, not a reading task.
3. `0x10092ca0` the animal creation helper (terrain tests `type +0xac(0) == 0x46` or `type +0x5c() == 0x145`, the manager's creation slot `+0xa0` with float x/y).
4. The route 62 (`HIRSCH`) animal class: its tick body (movement, any draw) and the meaning of the two flag bits `+0x8c(0)` bit 1 (value 2) and bit 2 (value 4).
5. The `HIRSCH` loader `0x100946c0` (8-byte entries -> 16-byte spawn objects, vtable `0x100cac04`) and how those objects reach `0x10092ca0`.
6. The hunter building tick `0x10069f40`: gate, switches and the shape are read; the production arithmetic (units of the raw store `[+0x24]`, property pair `0x44f`) and the dispatch conditions are **not** decoded.
**Known about job 0xd (read):** entry `0x1003b0e0` (byte table `0x1003b480`, case `0x1003b1cc`, object `0x1005c610`); shared by the hunter (`0x10069f40`) and the fur trapper (`0x1006e5d0`); targets found by `0x10071da0(8)` (nearest figure in the radius whose figure-type goods equal the building's input 0); the kill step `0x100547e0` removes the target from the unit manager and adds **the animal type's capacity (`LOGIC[0x11] << 8`, FigurenHeader) to the hunter's cargo**, which the shared walk-home step credits to the home. **Unknown:** the pursuit steps' movement slots (`+0xe8`, `+0xd0`, `+0xc8`, `+0xcc`), the flag bits' meaning, the animals' tick.
**Questions that remain (owner/reader):** Q1 scope of the fauna sweep and its draws (decision); Q2 the animal class vtable behind route 62 (read); Q3 the production arithmetic of `0x10069f40` (read); Q4 what a failed kill (flag bit 4) does to the hunter's cargo and counter (read with the movement slots).

## Q3 answered: the hunter tick 0x10069f40, decoded (2026-11-06, read-only; vectors `fixtures/synthetic/sim/hunter_vectors.txt`, reference `tools/hunter_ref.py`)
Corrects "not decoded" above for the production and dispatch arithmetic. The class is `0x1006a9c0` / vtable `0x100c82a0` (tick = slot `+0x8c`); fields: `+0xa` stamp, `+0x18`/`+0x1a` outputs (u16), `+0x1c`/`+0x1e` reserved by carts, `+0x20`/`+0x22` activities, `+0x24` the **raw store** (u16, credited by slot `+0xc0` = `0x1006a490`: `add word [ecx+0x24], ax`, no goods test), `+0x28`/`+0x29` the two output-line switches (constructor: both 1), `+0x2a` the **split byte (constructor `0x40`, written nowhere else in this class)**, `+0x2c` the single worker pointer (attach/detach `0x1006a850`/`0x1006a8b0`: one slot of figure class `0x1500`).
**Per call (D):** (1) gate `(u16)(t - [+0xa]) >= 0x1f4` (`0x10069f5d`), `[+0xa] += 0x1f4`. (2) both switches 0 -> return (no decay). (3) both activities `a*127>>7`. (4) flag bits 4/5 -> return. (5) ratio: a worker pointer set -> 0 (skip production); else `min(0x80, raw*128/need)` with `need` = type `+0xe4(0)` (idiv); **below 0x40 -> starved: status 1, no production**. (6) `total = rate0 * ratio >> 7` with `rate0` = type `+0xe0(0)`: **only output 0's rate is read**; capacities from property `0x44f` (pair, `<< 8`). (7) line 0, if its switch is on and `cap0 > out0`: `share = split*total >> 7` added to `+0x18` (u16) and `share << 4` to the activity; line 1 likewise with `(0x80 - split)*total >> 7`; a full line reports status 2 (display). (8) **raw is consumed (`need*ratio >> 7`) only if a line produced.** (9) **a full ratio (0x80) returns: no dispatch**; (10) a worker out returns; (11) `0x180 / rate0 < raw / need` returns (signed idiv); otherwise the target search `0x10071da0(8)` runs, then the figure (job 0xd, figure type `0xb4(0,0)`) is created through `0x10072d20`, its cargo goods := input 0, and the new job's first step receives the target's id.
**Consequence for the data (stated, not a policy):** with the shipped 805 (rates 43 / 26, need 57, split 0x40) a full step makes 21 NAHRUNG and 21 TIERHAEUTE (the code splits output 0's amount 64:64 and never reads output 1's rate 26), per 57 raw. 17 hand-derived vectors, the independent reference agrees (0 disagreements); 8 reference mutants: 7 killed, 1 survives as an equivalent (capacity-before-starved ordering changes only the display status). **Not modelled:** the target search outcome (wildlife) and the job-0xd figure. **Open:** the meaning of property `0x44f` (read as the two capacities, consistent with 1024/1024 for 805), the message codes (display), and whether `rate0 = 43` truly applies to both lines in the running game (an original-runtime check would settle it: NOT_RUN).
