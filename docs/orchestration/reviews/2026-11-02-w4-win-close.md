## Actionable source findings

### [P2] Require evidence that the viewer script actually finished — tools/test/viewer_wiring.py:97–101

`ran_to_end` checks that the **input script** ends with `quit`, that no available
log line contains `FAIL`, and that the child returned zero. A missing log becomes
an empty list, so a program that never runs the viewer script passes. The public
CLI was exercised on this Mac with an executable containing only `exit 0`:

```text
viewer_wiring: PASS r1_held_publication: window exit 0 after 0.1 s, no failed step; session cache/review-w4-close/no-session
```

There was no session directory or `script.log`. This is a reproduced false pass,
not evidence that the reported real sessions failed to execute: `main.cpp`
separately rejects an unfinished script. Require complete, matching execution
records and test missing, empty, truncated and wrong-script evidence with a
zero-exit child, plus a genuinely complete positive control. Revalidate retained
sessions before deciding whether any needs to run again.

### [P2] Use actual SDL frame-delivery results for CPU visibility — src/app/src/viewer.cpp:1827

The newly added CPU consumer calls `visibility().frame_done(true, fresh, fresh)`
after ignoring the return values of `SDL_UpdateTexture`, `SDL_RenderTexture` and
`SDL_RenderPresent`. SDL3's local header declares `SDL_RenderPresent` as returning
`bool` for success/failure. Consequently a failed present, or presentation of an
old texture after an update failure, can settle a command as `Visible` and remove
its pending note. The GPU consumer checks present status; the CPU consumer must
also account for the actual delivery chain. The pipeline unit test accepts an
injected `present_ok` argument and therefore cannot detect this viewer wiring bug.
Exercise failures through the production CPU viewer and prove that a subsequent
successful frame completes the same command. A forced-success mutant must fail.

## Evidence-contract gap: capture failure independent of child failure

`tools/bench/dev_session_capture.py:135–144` discards `capture()`'s Boolean result
and returns the child's exit code. Its documented CLI promises child status;
the problem is that C4 has not established an independent capture-completion
verdict. All three native capture fixtures in
`tools/test/window_tools_contract_test.py:109–165` exit 9, including the successful
capture control. They prove preservation of that status, not rejection of an
incomplete capture when the child succeeds.

A portable control-flow probe executed the unchanged `main` function with mocked
Windows calls and a zero-exit child. It produced `cmd1: REFUSED`,
`window_exit=0`, and tool return 0. This is not a native Windows execution.
For closeout, the policy is explicit: an incomplete requested capture must have
a non-success aggregate result, with the actual child status recorded separately
and preserved when already nonzero. Add native zero-exit success/refusal controls
and the separate nonzero-child control. Missing requested captures and a size
mismatch must not produce a success artifact. This is a small wrapper/contract
correction, not another rendering matrix.

## Decisions on the two historical failures

### A — preserve the complete corpus; schedule its cost honestly

The instrumented run reports all 5,492 assertions passing in approximately
5,100–5,400 seconds, beyond the old 3,400-second limit. The report now discloses
overlapping WSL work, the clock step, uncommitted diagnostic provenance and
unchanged executed dependencies. It supports a test-scheduling decision; it is
not a clean final-head canonical whole-app sanitizer pass.

Approve the `heavy` classification for exactly these two full-corpus app cases:

- `play: islands are the ones the sim placed`
- `play: tick 0 matches the viewer except objects the sim did not place`

Give these cases an **8,000-second per-test timeout in ASan/UBSan builds**. Keep
every scenario and assertion. No reduced corpus, global timeout increase or
silent exclusion. The ordinary sanitizer lane plus the dedicated full-corpus
lane must reconcile to the complete required app inventory. Verify generated
CTest labels/timeouts before launching the expensive lane; run it once after
cheap contracts and final source freeze, serially within existing admission.

The current WSL sanitizer build has the viewer disabled. A viewer-enabled,
instrumented CPU/SDL-dummy run of the real viewer cases and input tests is also
required. Compiling a helper library under sanitizers does not cover `viewer.cpp`.
These are two distinct coverage gaps.

### B — close the identified mechanism, retain the limit on historical attribution

The process-wide baseline can include earlier cases' waiting generations.
Draining them after the baseline explains an unsigned wrap and unequal final
counts. The new settling/signed-arithmetic fix is relevant. Its regression does
not exercise the stalled case's actual baseline call site, however, and the case
still omits the diagnostic counters requested in C3.

Require one gate-controlled regression through that actual case path, with a
valid control and removal of its settling call caught by the intended assertion.
Record before/current waiting, in-flight and byte counters at relevant failures.
Do not depend on the new helper test's 50 ms sleep to prove ordering. Keep cleanup
safe on every exit. No production reclaimer redesign is authorized.

**Historical disposition:** the original failure remains preserved as consistent
with this mechanism, but exact attribution is unrecoverable without the missing
counters. After the actual-path regression and affected gates pass, this is a
documented historical uncertainty, not a requirement to recreate an unlogged
incident indefinitely. A new unexplained lifecycle failure still blocks closure.
