## 3. Gaps found (the plan's reason to exist)
1. **No deposit source in shipped scenarios (T, D).** `Island::deposits` is filled only by hand-built specs: the loader makes no deposit from `BERGWERK2` (`UndecodedDeposits`, OQ-024) and does not turn the `OCCUR` ore objects into deposits. In the original the deposit is an island object (class `0x100637a0`) whose goods are its object type's ware, found by `0x100787c0` among the island objects of kind mask 1 (= ERZSYMBOL, the same objects as `ore_objects`). **Open (U):** whether the original deposit amount comes from the `OCCUR` u16 (shipped values are 2,000 or 400 t; 2,000 equals the constructor default `0x7d000`) or is always 2,000 t, and who clears the reserve flag (OQ-035 b, c). Today `create.cpp` finds `find_deposit(island.deposits, ...)` which is empty on every shipped island, so a mine created by the loader or a command is idle ("missing input").
2. **Mine placement is Unsupported (D).** Class `0x3000` (flag word `0x3096`: 8 `MINE`, 4 `STEINBRUCH` types) reads the type's `HIGHMAP` table at type `+0x234` (16 entries in `Anlagen.dat`; also `Data/Highmap.dat`) through `0x10008a80`, `0x10008d90`, `0x10016d60`, comparing a stored byte with `ftol(...) - (arg & 0xff)`. `docs/re/ship-placement.md` section 3 lists it as **Unsupported, explicit**; `placement.cpp` accordingly refuses these types. The terrain/mountain/height rule, the orientation rule and the relation of the mine footprint to the ore object are unread.
3. **Mine creation by command (T).** `create_building` attaches the Mine payload and calls `find_deposit` over `island.deposits`; with gap 1 closed it would pick the ore. Whether `BuildCmd` of a Mine is otherwise complete (payment, permission, claim of the footprint) follows the ordinary path (T: cloth/leather builds) but is untested for class `0x3096`.

## 6. Compatibility plan (decision requested; nothing landed)
State 133 is the baseline and is not amended; no shared version is allocated here. The planned runtime work changes **accepted-command outcomes and world evolution**, so by the project contract it needs an integration identity decision **before landing**:
- X2 turns the refusal of `BuildCmd` for class `0x3096` into an accepted command (accepted-command outcomes change).
- Closing gap 1 gives mines (imported and built) a deposit where today they have none: every existing scenario with a working-looking mine would start producing, which changes world evolution and state hashes of existing recordings, and (depending on the representation chosen) may add saved state (a deposit list derived from `ore_objects`) or change the meaning of the saved `Mine::deposit` index.
- A content/registry digest does not change unless a deposit table or rule becomes data; PRNG: no draw is expected (the Mine tick draws nothing; `docs/re/production.md` 4.4), to be confirmed in X1.

Options for the orchestrator (my recommendation first): (A) a new integration identity (one version bump, allocated by the orchestrator) for the whole salt slice, with old recordings immutable and refused with their own text; (B) gate the new behaviour behind a rules flag (default off) so 133 saves and worlds evolve exactly as before, at the cost of a persisted rules bit (itself a saved-state change); (C) hold X2-X5 at tests-only fixtures built from hand-made `DepositSpec`s without touching the loader or the command path (no identity change, but it would not prove the player-built path on shipped scenarios). **I will not start X2 engine work until one is chosen.** Independent research, the contract, the Python reference and the hand-derived vectors (X1) and fixture work proceed meanwhile.
