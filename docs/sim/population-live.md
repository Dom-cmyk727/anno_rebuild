## 2. Resident supply: facts (D, section S1-S4 of the research)

**House demand** (`+0xa4`, `0x100765c0`): `Menge * E * 256 / 44236 - stock / 16` (D, population.md §5), signed, in the same 8.8 units a delivery adds (a delivery adds `amount * 16` to the stock, so `stock/16` is in delivered units).

**House choice** (`+0xd4`, `0x10076670`), `(supplier, &goods_out) -> score`:
1. `A = supplier.type.out0`, `B = supplier.type.out1` (the type's two WARE goods).
2. **Skip rule:** over the house's walker slots, each walker's cargo slots `0..n-1`: a slot with goods `gid` and a **non-zero amount** zeroes `A` (if `gid == A`) or `B` (if `gid == B`). The calling walker is one of those walkers. **D (cargo vtable `+8` = `0x10037570` returns the u16 amount):** the test is "amount != 0, then goods == A / B"; a slot that holds goods with amount 0 (a purchase that returned 0) does **not** exclude its goods.
3. Per candidate good `g` (A first, then B), `slot = lookup[g]`; skip if `slot >= n`. `s = min(trunc(1536 * stock[slot] / (E * Menge[slot])), 160)`, `urg = 128 - s` (range -32..128). **IdSec chain:** `urg = max(urg, urgency of lookup[IdSec(Ware(slot))])`, recursive along the chain (helper `0x10076960`), signed. Accept `g` only if all hold: `urg >= 0`; `supplier.avail(g) > trunc(R * Menge * 256 / 4096)` with `R = trunc(res64/64)` (signed, strict); `supplier.enabled(g) != 0` (`+0xc4`). Accepted: `*goods_out = g`, `best = urg`. `B` is accepted only if its `urg` is **strictly greater** than `best` (a tie keeps `A`). Result `best`, or `-1` when nothing was accepted.
4. Callers require `score >= 0xc` (12), i.e. `s <= 116` for a good with no IdSec boost.
5. **Domain (P, new policy, section 12):** the original has no `E == 0`/`Menge == 0` guard here (divide fault). The engine treats a candidate whose divisor is 0 as a **fault** like section 7 (`HouseFault::ChoiceDivisor`), never as "not chosen"; the registry already forbids `Menge == 0` (population-contract §3), and `E == 0` is reached only by crafted state. **IdSec recursion** is bounded: the chain is followed at most `goods_count` steps and a cycle is cut at that bound (the original recurses unboundedly and would crash; **P**). Registry validation reports an IdSec cycle among *needed* goods as a content error (**P**).

**Supplier availability** (`+0xa4(g)`, 8.8): MarketStall (PRODTYPE 161): the full city store of `g` (`city.stock[g]`, no reservation, no range check). PublicService, School, Doctor: the constant **256** for any `g`. FireBrigade: 512. Inn: its tavern stock `u16 +0x18` (g ignored). Plain/others: 0. Enabled (`+0xc4`): MarketStall reads `flag[out0 != g]` (the bytes test `out0 != g`: goods == output 0 reads flag `+0x18`, **every other goods reads flag `+0x19`**; default 1 each; the ALL `0x8e` arm = either flag with a non-zero output is not modelled), Castle `+0x22` (not read by anything reachable now), all others 1. **U:** who flips the stall flags (setter `+0xc8` not read) - the engine keeps both at 1.

**Walker purchase** (step B arrival `0x10056480`, D): building at the walker's tile with city mask `0x21` (none: nothing happens, job continues). Cargo slots `n = figure type slot count`. Find the first empty slot `i` (empty = goods 0). If none, done. Slot `i`: `score = choice(bld, &g)`; if `score < 12` return. `amt = min(bld.avail(g), house.demand(g), capacity)` (all signed 32); if `amt > 0`: set the slot's goods `g`, `r = bld.bill(g, amt, third)`, **add** `r` to the slot's amount (`+0xc` is `+=`; an empty slot has amount 0, so the result is `r`), then `i += 1`. **Second pass:** if `i < n` and slot `i` is empty (goods 0), re-run the choice (when the first `amt` was `<= 0` this is the **same** slot with the same inputs and no effect; when it was filled the walker's own cargo now excludes `g` and `i` is the next slot), same `score >= 12` gate, same `min` and bill. At most two purchases, no third pass. A bill that returns 0 leaves goods set with amount 0 (the slot is non-empty). The third bill argument (`BGruppeNr`) is ignored by every billing class.

**Billing** (`bill`, city slot `+0x88` = `0x1002dac0`, args `(goods, amount, third, take)`, D):
```
if goods < 0x1a or goods > 0x28: return amount            # nothing billed, nothing taken
rec = city.goods_record[goods]
rec.billed += amount            (u16, the REQUESTED amount, before clipping)
if take == 0: return amount
t = min(amount, rec.store)      (unsigned)
rec.taken_stat += t (u16); rec.store -= t; return t
```
Wrappers: MarketStall `take = 1` (returns `t`); PublicService and School `take = 0` (return `amount`; School also bumps a statistic, U effect); Doctor/FireBrigade return 0; Inn (`0x100756e0`): `t = min(tavern_u16, amount)`, taken-stat `+0x1a += t` (U, not modelled), `tavern -= t`, then bills its *input* good (type slot `0xb0(0)`) with the **clipped amount `t`** and `take = 0` (even when `t = 0`: `billed += 0`), returns `t`. Consequence: a church/chapel/school/bath/theatre supplies `min(256, demand, capacity)` of its own infrastructure good **without consuming anything**; a stall consumes the city store.

**Billed counters and `save_billed_goods` (owner 2026-10-25, default true; A):** `billed[g]` (consumer goods `0x1a`-`0x28` only; u16 in the original, widened to u32) is accumulated per city and consumed by the tax pass, which is *outside this task*. The engine adds `City::billed` (vector sized `warehouse_goods`) and a rule `save_billed_goods` (default **true**): true = `billed` is saved, hashed and restored; false = it is *not* saved (a loaded city starts with zero billed), reproducing the original's dropped scratch. Either way the live tick writes it. Both values are tested.

**House delivery** (`+0xc0`, `0x10076610`, D): `goods -> slot = lookup[goods]`; if the goods has a slot, `stock[slot] += amount * 16`; if the goods has an `IdSec`, the replay at `0x1007664c`-`0x1007665d` is `call *0xc0(vtable)`, and house vtable slot `0xc0` (`0x100c9958`, entry `0x100c9a18`) is `0x10076610` **itself**: a recursive deliver of the substitute, which replays the substitute's own `IdSec` in turn, and a substitute without a need slot ends the chain. A chain 26 -> 27 -> 28 with amount 100 raises all three slots by 1600. The original recurses unboundedly (a cycle crashes it); **P-3:** the engine follows at most `goods_count` replays after the first add and cuts a cycle or self-loop there, checks every add of the chain before applying any, and refuses the whole call on a u32 overflow. A good the house does not need returns 0. Step C arrival (`0x10057d70`): for cargo slots `0..2` with non-zero goods, `home.deliver(goods, amount)`. Widened/checked (A): a delivery that would leave `u32` is refused whole and counted.

## 5. Upgrade, Downgrade, SetGroup, removal (D, research T1-T3)

**UpgradeCheck** (`0x10075dd0`): `NoUpgrade` -> 0. Scores use cap **128**, signed idiv. Goods loop: next-group needs `j = 1 .. next.goods_end-1`, **forced** only, the score taken at the **current** group's slot `lookup_cur[Ware_next(j)]` with the **current** record's `Menge` (a missing current slot is a data-invariant violation: **P-3** a fault, never "not eligible"). Infra loop: `next.goods_end .. next.infra_end-1`, forced only, `min_infra` starts 160 (scores are <= 128); a need whose ware is the tavern role also joins the goods sum/count. Food uses the **next** group's `Menge[0]` and the house's slot-0 stock. `f = Nahrung_next[(food+4)>>3]`, `mean = count ? sum/count : 128`, `b = Bedarf_next[(mean+4)>>3]`, `i = Infra_next[(min_infra+4)>>3]`; require `f > 0`, then `b > 0`, then `i > 0` (strict). Then city `+0x94`: queue count `< 10` (always true: the queue is never filled), the house kind in block `0x61..0x80` (**A:** the engine's equivalent is "the house type belongs to a house group with a next group"), and the next type (`id - id%20 + 20`) exists and its materials are available (`0x1002c030`): for `k = 0..4` (goods `0x29+k`) with `amount_k = nextType.material(g)` (bytes `type+0x1e..+0x22`, tons<<8, of the **base** next type, never the variant), a non-zero `amount_k` must satisfy `amount_k <= store[g] - reserve[g]` (signed), where `reserve` is the dword at `city+0x5d4+8k` (the build-goods *setting*; writers: the constructor and the city read path; 0 unless a scenario or the build-goods setting sets it, state.md `BuildGoods.setting`) - **not** the cumulative spent, which Upgrade books into the neighbouring dword `+0x5d8` and which the check never reads. The queued materials (`0x1002bf60`) add to `amount_k`; the queue is always empty.

**Upgrade** (`0x1002cbe0`, immediate): next type `id - id%20 + 20`; none -> nothing happens. **It re-runs the materials check `0x1002c030`; if it fails, nothing happens: no spend, no draw, no counter change** (the UpgradeCheck result `1` is still returned to the tick). Materials: for `k = 0..4` (goods `0x29+k`): `spent[k] += amount_k`; `store[g] -= min(amount_k, store[g])`. **Variant:** property `0x32` (count `c`, step `s`): if `c != 0`: **draw** the world PRNG, `idx = r mod c` (unsigned), new type = the type `base id + idx * s` (no materials re-check for the variant type; a null variant lookup is not checked in the original. **P:** the engine validates at registry build that every variant type of every house type exists, so the case cannot arise; it is never handled by refusing after the spend). Then in this order: `counter.sub(oldG, trunc(res64/64))`, `houses[oldG] -= 1`, detach old type, attach new type, `SetGroup(oldG + 1)`, `counter.add(newG, trunc(res64/64))` (res read **after** SetGroup), `houses[newG] += 1`. The PRNG draw is the **variant draw only** (SetGroup's own draw is first-assignment only). `UpgradeCheck`'s "one-predicate near misses": a strict `> 0` table entry, a forced need below the score threshold, a missing material, a missing next type.

**Downgrade** (`0x1002cdd0`): previous type `id - id%20 - 20`, else `id - id%20 - 19`, else nothing. Same variant draw (before SetGroup), same counter/house-count/SetGroup/type swap, no materials. **SetGroup** (`0x10076b90`): carry each old need's satisfaction `min(stock*1536/(oldMenge*E),160)` by goods id (also to the IdSec chain when `>= 102`); new stock `trunc(newMenge * s * E / 1536)` (widened); new needs get 0 except food (slot 0) `Menge*E/12`; **upgrade** keeps residents and `E`; **downgrade** gives new needs `s = 102` and sets `E = trunc(res64/64) << 7`. **First assignment** (the old group is null; reached by the Create path for a non-pioneer type, population.md §5): if the new group number is not 0, residents := `Wohnmax << 6`, `E := Wohnmax << 7`, and for every new need with the forced byte set the world PRNG is drawn once, satisfaction `128 - (r & 31)` (site `HouseFirstAssignment`); non-forced needs get 0, food (slot 0) `Menge*E/12` as above.

**Removal** (island `+0xcc` = SetHitPoints `0x10093c10`, `hp = 0`): destroys the house through the owner city's remove-at-tile `0x10028fd0` -> building-index remove `0x100255c0`, which **subtracts** `trunc(res64/64)` from the group counter, decrements the house count, removes the building and **detaches** the walkers (house destructor `0x10075bc0`: for each of the 4 slots `house.detach(fig)` `0x10075b70` clears the slot, then `fig.vt+0x2c(house)`; **the callee for a house walker (D, L4 review P2-3):** the FigurenHeader `BEWOHNTYPE` of the walker ids (250, 252, 293-305, 324-329) is `ZIVILIST` = class code 33, factory `0x1009a110` case 5 (`0x1009a441`: `new(0x88)`, constructor `0x10054030`, vtable `0x100c6a98`); that vtable's slot `+0x2c` is `0x10053ff0`: if the argument's class id (slot `+0x14`) is `0x1a00` (a building) and it equals the figure's home field `+0x84`, it stores 0 there, otherwise it forwards to the base `0x10001030`. It does nothing else, so detach = clear the home (the figure's own end path `+0x110` = `0x10053f50` calls the same slot `+0x2c` on the home, then zeroes `+0x84`); the figure is NOT ended, it lives on with home none, as workshop and farm figures do, OQ-131 - L3 review P2-1). Quirk (**P-9**, U): a damage record that already exists with hp 0 makes the call return silently; the engine has no damage records, so removal always proceeds. The engine reuses `remove_building`; the new parts are the counter subtraction (derived counters make it automatic) and the explicit walker detach (slot cleared, the figure's home becomes none, the figure keeps walking: its body ends it at the arrival or at its next visit without a home and delivers nothing; the engine does not model the original's 15.0 walk before an end outside the home).

## 5a. SetProperty 0x21 on the player (D `0x10020d51`-`0x10020ecb`; L4 review P2-2)

Read from the disassembly (`this` = player `esi`, `edi` = the property buffer, `v` = its dword at `+4`, `L` = the u16 at player `+0x96`, `b` = the byte at `+0x95`):
1. Clear: `L` bit 0 clears `v` bit 24, bit 1 -> 25, bit 2 -> 26, bit 3 -> 27, bit 4 -> 28.
2. `v` bit 24 present: `L |= 0x801`, event `0x1f`. `v` bit 25: `L |= 0x1002`, event `0x1e`, then `L |= 0x2004`, `b = 4`. `v` bit 27: `b += 4`, `L |= 0x4008`. `v` bit 28: `b += 0xc8`, `L |= 0x8010`.
3. Restore from the high byte of `L` (`+0x97`): bit 3 -> `v` bit 24, bit 4 -> 25, bit 5 -> 26, bit 6 -> 27, bit 7 -> 28.
4. If `v` bit 27 is set, set bit 26; if bit 28 is set, set bit 26. Store `v` at `+0x90`.

**Stored value in the engine (P-12).** The latch makes bits 24-28 sticky: every bit 24-28 that was ever present is cleared in step 1 and restored in step 3, so for a monotone player value (the engine only ever ORs the city mask in) the clear-and-restore is a no-op, and the only value effect is that bits 25, 27 and 28 also set **bit 26** (bit 25 via the `+0x97` bit 5 restore of step 3). `player_flags_set` implements exactly that; `stage_pass` stores `player_flags_set(flags | city_mask)`. The latch bytes, the byte `+0x95` (read by nothing reached) and the events `0x1e`/`0x1f` are **not modelled**; the divergence is exact unless something other than this setter lowers a bit 24-28 of `+0x90` (the HEAD import writes `+0x90` directly; the engine has no such writer after load). Consequence: unlocking stage 25, 27 or 28 also sets bit 26 of the player mask, which the kernel's need loop reads. Tests: `house_live_test.cpp` "SetProperty 0x21 also sets bit 26", hand-derived values (0x2000000 -> 0x6000000, 0x8000000 -> 0xc000000, 0x10000000 -> 0x14000000, 24 and 26 unchanged) and the stage pass for stages 24-28.

**Fault channel.** `Effects::faults` (`FaultRecord`: `HouseFault`, kernel `reason`, `ResidentFault`, building, figure, goods) is merged in issue order; the first record sets `World::faulted()` (state: hashed and saved) and `World::fault()` (a diagnostic text, not saved). A fault **stops the world**: the advance finishes only the current island's merge, every later advance changes nothing (not even the clock), `check_invariants()` returns `world fault: <text>` while the text exists, and tick/ring/city/House skip any work after a fault inside the same island tick (the rest of that island tick - sweeps, the 300 s event, the drought - still runs; the advance ends right after its merge). `ResidentFault` in the choice, the bill/add and the delivery merge uses the same channel (the counted-and-skipped interim of L2 is replaced; `ResidentStats::faults` is kept as a diagnostic count). A `NotEvaluated` kernel result, a typed `HouseFault` from the handlers, a missing serial context (`HouseFault::NoSerialContext`: the contexts of the commands' seams carry none) all fail loudly, never skip or clamp. A reloaded faulted world reports only `faulted()`.

### 20.5 Scale and proportionality

Per-search work is a function of the house's own surroundings: in `population_scale_test.cpp` a house in a 4-block world and the same house with ten times the content (36 more blocks in its city, a second island with 20 blocks) do **identical** work for their first search: 1 rectangle query, 1 hit, 1 candidate scored and accepted, 1 walk search, 256 expansions (asserted equal; the search happens at tick 2561 versus 2673: unrelated content changes only WHEN a house is visited). One kernel call per visit in both. Doubling the houses (8 -> 16, same blocks) doubles the taken gates (32 -> 64), spawn draws (8 -> 16), searches, candidates scored and expansions (2048 -> 4096) exactly; **visits do not double** (384 -> 428): the building scheduler visits `clamp(d * n / building_div + 1, n)` slots per city visit (the original's rule, `building_div` 500), so below a few hundred buildings the "+1" dominates; the work a visit causes is what scales. Wall time of the bounded workloads: 8 houses 0.024 s, 16 houses 0.028 s for 12 000 ticks (Debug, Mac); the canary rows above for real maps; the 150 000-tick search ran 306 houses (`single32`) in 20.8 s. No claim about late-game multiplayer scale.

**Mod-defined content** (`population scale: a mod-defined ...`): PRODTYPE 99 as group 2 of a three-group table, needs on goods 29 and 30, figure types 7001-7003, a MarketStall type 8890 offering 29 and 30; it spawns, buys, bills and delivers end to end with the same ledger equations; no shipped id is read.

**Audit of the House and resident path for full-world or quadratic work** (grep of `house_tick`, `house_transition`, `resident_job`, `resident`, the merge, `Scheduler`): per house visit: the kernel (O(needs)), `rect_query` over the house's own square (a grid walk of at most the square, then a sort of the hits), `house_choice` per candidate, one walk search over cells of that square (`WalkCells` is built per search: O(square)), `others_cargo` over the house's walker slots. **No per-visit scan of the city, island or figure registry.** One real violation found and fixed: the stage pass called `residents_at_or_above` once per stage record (31 x every building of the city per gate); it now counts all groups in one pass (`residents_at_or_above_all`, test). Local, not world-size, costs left as they are: `choose_stand` looks up goals with a linear `find_if` per visited goal and removes duplicate entrances quadratically in the number of candidates of one square (bounded by the square: 33 x 33 tiles for the 16-tile pioneer radius); `add_figure` takes the original's hint scan (worst case O(figure slots) when the list is full, amortised small). `check_invariants` and the diagnostic records are O(world) by purpose and run only in tests.

**Serial path:** the whole House path, the resident figure body and the stage pass are **serial**: `World::advance` runs the islands one after the other, `island_tick` -> `city_ring_tick` -> `city_tick` -> `building_scheduler` -> `house_tick`, and the figure phase is one serial pass; `house_tick`/`stage_pass` write the player table and the figure registry directly (section 19). The measured throughput above is single-threaded.

### 21.2 First assignment, hand-derived (D, `docs/re/population.md` 17)

Original order in a player build: Place charge (`0x10027a77`-`0x10027ad4`) -> Create: property 0x23 stamp (`0x100246ae`), position, list insert, house count++ (`0x10024c2d`), then SetGroup(group record `kind - 0x61`) (`0x10024c3c`). SetGroup with a null old group: group number 0 skips the draw block; otherwise per need j in `0..infra_end-1` with Force: one draw `sat = 128 - (r & 31)` in need order, then `E = Wohnmax << 7` and `residents_64 = Wohnmax << 6` (16-bit stores in the original), then `stock_j = trunc(Menge * sat * E / 1536)` for satisfied needs, `trunc(Menge * E / 12)` for slot 0 if unsatisfied, 0 otherwise. **Group number 0 ALSO skips the E and residents_64 stores** (`je 0x10076dca`); the 320 / 640 of a pioneer house come from the House constructor `0x10077220` (stores at `0x10077234` and `0x1007723a`), not from SetGroup, and the 2186 below depends on that E. Group 0 (E 640): `trunc(41 * 640 / 12) = 2186`. Shipped SIEDLER (Wohnmax 15, E 1920, residents_64 960): six draws (needs 0,1,2,3,6,7), all `r & 31 = 0` gives stocks 5920, 1920, 3200, 1280, 3200, 6560 for needs 0,1,2,3,6,7 and 0 for the unforced.

The original-equivalent domain (Wohnmax < 512 so `Wohnmax<<7` fits u16, u16 stocks) is NARROWER than the overflow-free preflight domain below; the engine widens and does not reproduce the 16-bit wrap. **Domain preflight (G3).** The original wraps silently in 16 bits; the engine widens and must refuse instead. Because `sat <= 128` for every draw, the worst case is independent of the draws: require `Wohnmax << 7 <= u32 max`, `Wohnmax << 6 <= i32 max`, and for every need `Menge * 128 * E / 1536 <= u32 max` and `Menge * E / 12 <= u32 max`. Computed from group data only, so it is a registry/activation error (`house_updates_problem`) naming group and need, and again a runtime preflight in the BuildCmd validation phase (before charge, serial and draw). No limit beyond overflow is imposed. For G1 and G3 the preflight is recommended over a transactional proposal: it needs no PRNG rollback and keeps the legal draw order bit-identical.

### 21.3 P-14 and P-15 (replacements to implement in C3)

**P-14.** Original (`0x1002e080`, `0x1002e000`, `0x1002cbe0`): the current-kind predicate is only `PRODTYPE in 0x61..0x80` (and queue < 10); the next type `id - id%20 + 20` need only EXIST and have materials; Upgrade never checks that the new type is a House or of group + 1 (it calls SetGroup(group + 1) regardless). Shipped audit (`cache/map2-pop-close1/C0/audit_ladder.txt`, 81 house-kind types): 7+7+8+8 ladder types (501-513 -> 520.., 520.. -> 540.., 540.. -> 560.., 560.. -> 580..) are legal; 6 types 580-585 and 33 scenery types (3001, 3101, 3203 ...) have no next type (terminal; also KAUFLEUTE/ARISTOKRATEN `NoUpgrade`); **irregular**: 3851-3854 -> 3860 (PRODTYPE 289, plain 3x1), 3960/3969/3972/3979 -> 3980 (market stall), 3951-3954 -> 3960 (a group-0 house, different footprint). The read code (`0x1002cbe0`, `0x1002e000`, `0x1002e080`) performs no kind or group check; `0x1002c790`, house vt `+0x28`/`+0x2c` and the tick's upgrade check `0x10075dd7` were not read; the runtime outcome is NOT_RUN. Note 3960 is both a successor (of 3951-3954) and itself irregular (-> 3980): declare irregularity per type, not per family. Replacement: classify every house-kind type once at registry build as `Ladder` (next is a House of group + 1, same footprint), `EndOfLadder` (no next type, or the group flag NoUpgrade) or `Irregular`. `Irregular` types are accepted only if the registry declares them (the original loader declares exactly the audited types, recorded with reason `original_non_ladder_successor` and part of the digest); an undeclared irregular successor (mod data) is a content error at `house_updates` activation naming type, next id, next PRODTYPE and group, and a typed `HouseFault` at runtime, never a silent not-eligible. Declared irregular and end-of-ladder houses are a counted, named outcome (not eligible), kept distinct from a fault. Tests need one real legal upgrade, one deliberate terminal family, one declared irregular, one undeclared mod case that faults.

**P-15.** The original search is directional: the exits allowed from a subcell depend on the arrival direction and constraint helpers clear single directed members (`docs/re/transport.md` around 1465-1490 and 1580-1600), so reversing a route found from the home toward the walker is not proved legal. Replacement: keep a forward-correct route as the contract. (1) Prefer the shared forward search from the walker with the goal being the entrance subcell INCLUDING a blocked entrance subcell as a reachable goal (the failure was the goal, not the direction), or (2) keep the reverse search but verify every consecutive pair of the reversed route with the same directed transition predicate used by the search (arrival-direction mask plus veto) and discard the route if any edge fails. Entrance semantics: the walk ends when the figure's tile lies inside the home's footprint (`0x10057ae0`); the endpoint must be an entrance point of the home, reached by a legal step; start inside the footprint needs no walk. Required controls on a small real terrain/entrance reproducer: adjacent-edge directedness, legal entry into the home, disconnected terrain gives no path (counted), a changed obstacle changes the route, no forbidden terrain and no teleport (every step is one subcell). Shared cart and harvester routing stays untouched; any change needs their regressions. Not measured in C0: how often a reversed route is illegal forward (needs the C3 checker).
