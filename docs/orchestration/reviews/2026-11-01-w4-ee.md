## Findings

### R1 [P2] Read outcomes and resources at a consistent publication boundary

`src/app/src/viewer.cpp:1236–1242` reads the outcome and then the snapshot,
claiming that the snapshot must be at least as new. `PlayRunner::publish` actually
records outcomes before swapping the snapshot, under different mutexes. A mouse
event or ordinary frame during that interval can therefore show Applied beside
pre-command money/goods. The wake sent after publication does not exclude those
other readers. A probe against the current libraries observed outcome sequence 1
with snapshot `outcomes_next=1`, tick 0, in all three trials. It used 10,001 cheap
refused commands to widen the observable interval; the ordering defect also
applies to paid builds. Provide a consistent read or defer the newer outcome
using the snapshot's publication watermark. Never wait on the sim from the
window. Test the interleaving with a barrier and an actual paid-build control;
the existing title test reads only after synchronous `run_n` returns.

### R2 [P2] Keep visibility pending through chunk replacement and presentation

`src/app/src/dev_feedback.cpp:296–310` treats a followed turn and zero pending
object-list builds as drawn. That does not establish fresh CPU chunks, GPU uploads,
the end of a dissolve, or a successfully presented frame. `DevScript::step` uses
the same shortcut for `wait drawn`, so a screenshot/checkpoint can run while old
chunks still draw. The barrier test clears the note without rendering any frame.
Reuse the existing frame/chunk readiness boundaries in `viewer.cpp` and
`window_trace` rather than inventing a second definition of visible. Cover a
committed scene with held chunk workers, constrained uploads, and failed present;
only the matching successfully presented replacement may satisfy the visible
case. Explicitly distinguish offscreen, superseded and no-visual-change commands.
Present-call success is still not physical display time.

### R3 [P2] Reject oversized footprints before materializing their tiles

`src/app/src/dev_feedback.cpp:188` constructs the entire `footprint_at` vector
before testing whether it fits the island. The registry permits nonzero 32-bit
dimensions. A 1,000,000×1 definition on a 30×30 island was accepted by the registry
and took about 22 ms in the current Debug path merely to report that it cannot
fit; larger dimensions can exhaust memory before the promised refusal, and
coordinate addition can overflow. Check the rotated rectangle with widened
arithmetic first, and avoid allocating a tile vector for an occupancy query.
Exercise huge dimensions under an allocation/work guard, not by actually trying
to allocate gigabytes. Keep legitimate larger content data-driven.

### R4 [P2] Avoid rebuilding city occupancy for unrelated edits on the window thread

`src/app/src/viewer.cpp:1386–1388` calls `PlacementKnowledge::update` on every
changed global building version, even while the tool is disabled. The update
clears and reconstructs the selected island's complete tile set and scans the
whole published list. An edit on another island therefore rebuilds an unchanged
large city on the window thread. In a bounded synthetic probe, an unrelated edit
caused about 1 / 5.5 / 19 ms of extra Debug work with 1,000 / 5,000 / 16,000
non-overlapping 2×2 local buildings. These are diagnostic costs, not Release
frame-rate measurements. The reported 100,004-building benchmark indexed only
four local buildings, so it does not cover this case. Use island-local changes or
bounded immutable preparation, avoid this work while disabled, and prove both
unrelated-edit isolation and correct same-island build/demolish updates. Do not
replace this with another full scan in a different window callback.
