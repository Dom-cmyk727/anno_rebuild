## 3. Gaps found (the plan's reason to exist)
1. **No deposit source in shipped scenarios (T, D).** `Island::deposits` is filled only by hand-built specs: the loader makes no deposit from `BERGWERK2` (`UndecodedDeposits`, OQ-024) and does not turn the `OCCUR` ore objects into deposits. In the original the deposit is an island object (class `0x100637a0`) whose goods are its object type's ware, found by `0x100787c0` among the island objects of kind mask 1 (= ERZSYMBOL, the same objects as `ore_objects`). **Open (U):** whether the original deposit amount comes from the `OCCUR` u16 (shipped values are 2,000 or 400 t; 2,000 equals the constructor default `0x7d000`) or is always 2,000 t, and who clears the reserve flag (OQ-035 b, c). Today `create.cpp` finds `find_deposit(island.deposits, ...)` which is empty on every shipped island, so a mine created by the loader or a command is idle ("missing input").
2. **Mine placement is Unsupported (D).** Class `0x3000` (flag word `0x3096`: 8 `MINE`, 4 `STEINBRUCH` types) reads the type's `HIGHMAP` table at type `+0x234` (16 entries in `Anlagen.dat`; also `Data/Highmap.dat`) through `0x10008a80`, `0x10008d90`, `0x10016d60`, comparing a stored byte with `ftol(...) - (arg & 0xff)`. `docs/re/ship-placement.md` section 3 lists it as **Unsupported, explicit**; `placement.cpp` accordingly refuses these types. The terrain/mountain/height rule, the orientation rule and the relation of the mine footprint to the ore object are unread.
3. **Mine creation by command (T).** `create_building` attaches the Mine payload and calls `find_deposit` over `island.deposits`; with gap 1 closed it would pick the ore. Whether `BuildCmd` of a Mine is otherwise complete (payment, permission, claim of the footprint) follows the ordinary path (T: cloth/leather builds) but is untested for class `0x3096`.

## 6. Compatibility plan (decision requested; nothing landed)
State 133 is the baseline and is not amended; no shared version is allocated here. The planned runtime work changes **accepted-command outcomes and world evolution**, so by the project contract it needs an integration identity decision **before landing**:
- X2 turns the refusal of `BuildCmd` for class `0x3096` into an accepted command (accepted-command outcomes change).
- Closing gap 1 gives mines (imported and built) a deposit where today they have none: every existing scenario with a working-looking mine would start producing, which changes world evolution and state hashes of existing recordings, and (depending on the representation chosen) may add saved state (a deposit list derived from `ore_objects`) or change the meaning of the saved `Mine::deposit` index.
- A content/registry digest does not change unless a deposit table or rule becomes data; PRNG: no draw is expected (the Mine tick draws nothing; `docs/re/production.md` 4.4), to be confirmed in X1.

Options for the orchestrator (my recommendation first): (A) a new integration identity (one version bump, allocated by the orchestrator) for the whole salt slice, with old recordings immutable and refused with their own text; (B) gate the new behaviour behind a rules flag (default off). **Withdrawn as an option: `Rules` is serialized and hashed (`state_fields.hpp` around lines 323 and 340), so a new bit changes the saved layout and the hash of every world; it is strictly worse than A.** (C) hold X2-X5 at tests-only fixtures built from hand-made `DepositSpec`s without touching the loader or the command path (no identity change, but it would not prove the player-built path on shipped scenarios). **I will not start X2 engine work until one is chosen.** Independent research, the contract, the Python reference and the hand-derived vectors (X1) and fixture work proceed meanwhile.

## 8. The narrower option, stated exactly (X1 prep, 2026-11-06; for the identity decision)
**Option N (narrow): place-and-bind only.** Scope: only a `BuildCmd` of a class-`0x3096` type that passes the (still to be decoded) mountain rule AND has a matching ore object in reach is newly accepted; at that moment the mine binds a deposit created from that ore object. Nothing else changes: the loader still makes no deposits, imported mines stay idle.
- **What must be saved.** Nothing new: `Island::deposits` and `Mine::deposit` are already in the state stream (a `Deposit` is `goods`, `x`, `y`, `remaining`, `reserve`; `Mine::deposit` an optional index). The command appends one `Deposit` (or re-uses the entry at the same tile when a second mine binds the same ore, so two mines never hold two copies of one ore) copied from the ore object, and sets the new mine's index. No new field, scope, registry data or draw site; `kStateHashVersion`'s layout is untouched.
- **What changes accepted-command outcomes.** Exactly one class: a `BuildCmd` placing a `0x3096` type (8 `MINE`, 4 `STEINBRUCH`), refused today with `Unsupported`, becomes accepted on sites that pass the rule and (for the salt slice) have a salt ore in reach, and stays refused elsewhere. No other type's outcome changes. Quarries have no ore: the binding step finds nothing and the quarry is not enabled by this option (it stays refused until separately specified).
- **What changes existing world hashes.** None for any existing world, save or recording that does not contain such a command: no deposit is created at load, no existing mine starts producing, no draw changes. A recorded log containing a `0x3096` `BuildCmd` would replay differently; the shipped fixtures contain none (to be grepped and asserted when the code lands; `goldens.txt` mentions `BuildCmd` generally). New worlds that contain the command differ by one `Deposit`, the new building and the production that follows.
- **What it cannot prove / residual risk.** Imported mines of shipped towns stay idle, so the "imported working mine" is not evidence either way; the finite-deposit amount (file value 2,000/400 t vs always 2,000 t) is a recorded adaptation until OQ-035 b/c is read; the add-on edition setting that makes deposits deplete must be read from the world settings, not assumed.
- **Does the project contract still call it an identity change?** The state layout, content digest and PRNG are unchanged, but the accepted-command behaviour changes, so the orchestrator must decide whether that alone requires a new version (options A/B/C of section 6 remain open). If the answer is "a version bump is required for any accepted-command change", Option N reduces to Option A with this smaller blast radius (no existing recording moves).

**Options A (loader-wide deposits from `ore_objects`)** is the one that moves every world with a mine: deposits at load change the saved lists and make every imported mine start producing; I do not recommend it for this slice.

## 9. X1 research status (2026-11-06; read-only)
- **Call site found.** The class-`0x3000` terrain arm is the tail of the type's placement-compatibility slot (`AnnoGame.dll 0x10008f90`-`0x100091d1`, arm at `0x10009199`-`0x100091c6`): it calls `0x10008a80(heights_ptr, stride, rotation, esi)` and returns `-1` (refused) when it returns 0, else the ordinary result byte `esi` (= `hi`, the highest cell minimum of the window). `0x10008a80` is called from nowhere else (xref scan of `AnnoGame/AnnoWelt/AnnoScene/AnnoFrame`).
- **Structure of `0x10008a80` (read instruction by instruction).** `this` = the type object; `w = byte[this+6]`, `h = byte[this+7]` (footprint); it walks `2h x 2w` half-tile sample cells (so the table has `4wh` bytes) in the order selected by the rotation (`rotation & 1` swaps the roles; four loops, one per rotation 0..3), reading the **HIGHMAP table** bytes sequentially (`this+0x234`, index `row*2w+col`); for each cell it forms a float sample position (constants at `0x10021780`, `0x100214ac`), calls the terrain height sampler `0x10008d90` (bilinear/triangle height from the byte vertex grid via `0x10015e90`) and `__ftol` (`0x10016d60`, truncation), and **refuses the site as soon as `table[cell] <= ftol(height) - (offset & 0xff)`** (`jle 0x10008d7b`), where the offset is the fourth argument (the window's `hi`). It returns 1 when every cell passes.
- **What is not yet decoded:** the float constants and the exact sample-position formula per rotation; the sampler's interpolation (`0x10015e90`); the table bytes themselves (the 16-entry `HIGHMAP` record in `Anlagen.dat` and `Data/Highmap.dat`) and their relation to the type's footprint; where the deposit sits relative to the footprint. `tools/placement_emulate.py` already executes real `AnnoGame.dll` bytes under unicorn; it skipped class `0x3000` only because the type object's table pointer was null, so the cheapest ground truth is to give the emulator a type object with the real HIGHMAP bytes and compare a new Python reference to it (the same method as the ordinary-land rule, 0 mismatches over 21,214 cases).
- **Deposit amount and reserve flag (OQ-035 b/c):** not yet read; the survey shows every shipped salt ore object has amount 2,000 or 400 (`OCCUR` u16); the next reads are the deposit constructor's callers (island object creation from `OCCUR`) and `0x10078960`.
- **Constants read (2026-11-06).** `[0x10021780] = 1.0f`, `[0x100214ac] = 0.5f`: the cell size is `1.0 * 0.5 = 0.5` tile and the centring offset `0.5 * 0.5 = 0.25` tile, so the sample positions are the centres `(0.25 + 0.5 c, 0.25 + 0.5 r)` of the `2w x 2h` half-tile cells, taken in the rotation's order. The sampler `0x10008d90` reads the four byte vertices around the position (`byte[p]`, `[p+1]`, `[p+stride]`, `[p+stride+1]`, each scaled by the third argument 1.0) and finds the height by a ray/triangle intersection (`0x10015e90`, x87 float code with epsilon compares at `0x100213c8`): float behaviour that the simulation must not reimplement from reading alone; the contract has to be derived by comparison with the emulated original (see above), and a deterministic integer formulation proved equal over the finite domain (heights are bytes in steps of 16, positions are multiples of 0.25) before any C++.

## 10. Additions to section 8 after the X0 review
- **Where Option N's derivation must live:** not in `create_building` (`create.cpp` around line 303), because the scenario loader's `build_island` shares that function and would then create deposits at load, i.e. Option A by the back door. It belongs in the command path (the `BuildCmd` apply step for the accepted type), after the placement checks and payment, before/with the building creation, and must be atomic with them.
- **Hashed side effect of the first appended deposit:** the island object manager stand-in (`state.md` A10, `ObjectManagerState.cursor`, hashed) visits `Island::deposits` with `cursor = (cursor + 1) % n` and visits nothing when `n == 0`. The first appended deposit therefore changes the cursor modulus from "no visit" to 1, only in worlds that contain the command; every other world is unchanged.
- **Recording scan (done 2026-11-06, probe not committed):** class-`0x3000` types in the registry: 1201, 1203, 1205, 1206, 1208, 1210, 1212, 1214, 1216, 1217, 1218, 1220.
