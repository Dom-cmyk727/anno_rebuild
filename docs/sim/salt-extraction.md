3. **Mine creation by command (T).** `create_building` attaches the Mine payload and calls `find_deposit` over `island.deposits`; with gap 1 closed it would pick the ore. Whether `BuildCmd` of a Mine is otherwise complete (payment, permission, claim of the footprint) follows the ordinary path (T: cloth/leather builds) but is untested for class `0x3096`.

## 9. X1 research status (2026-11-06; read-only)
- **Call site found.** The class-`0x3000` terrain arm is the tail of the type's placement-compatibility slot (`AnnoGame.dll 0x10008f90`-`0x100091d1`, arm at `0x10009199`-`0x100091c6`): it calls `0x10008a80(heights_ptr, stride, rotation, esi)` and returns `-1` (refused) when it returns 0, else the ordinary result byte `esi` (= the mode result: flag word `0x3096 & 3 = 2`, so `lo`, the LOWEST cell minimum of the window; an earlier draft of this paragraph said `hi`, wrong). `0x10008a80` is called from nowhere else (xref scan of `AnnoGame/AnnoWelt/AnnoScene/AnnoFrame`).
- **Structure of `0x10008a80` (read instruction by instruction).** `this` = the type object; `w = byte[this+6]`, `h = byte[this+7]` (footprint); it walks `2h x 2w` half-tile sample cells (so the table has `4wh` bytes) in the order selected by the rotation (`rotation & 1` swaps the roles; four loops, one per rotation 0..3), reading the **HIGHMAP table** bytes sequentially (`this+0x234`, index `row*2w+col`); for each cell it forms a float sample position (constants at `0x10021780`, `0x100214ac`), calls the terrain height sampler `0x10008d90` (bilinear/triangle height from the byte vertex grid via `0x10015e90`) and `__ftol` (`0x10016d60`, truncation), and **refuses the site as soon as `table[cell] <= ftol(height) - (offset & 0xff)`** (`jle 0x10008d7b`), where the offset is the fourth argument (the window's `lo`, see section 11). It returns 1 when every cell passes.
- **What is not yet decoded:** the float constants and the exact sample-position formula per rotation; the sampler's interpolation (`0x10015e90`); the table bytes themselves (the 16-entry `HIGHMAP` record in `Anlagen.dat` and `Data/Highmap.dat`) and their relation to the type's footprint; where the deposit sits relative to the footprint. `tools/placement_emulate.py` already executes real `AnnoGame.dll` bytes under unicorn; it skipped class `0x3000` only because the type object's table pointer was null, so (superseded by section 11: done) the cheapest ground truth was to give the emulator a type object with the real HIGHMAP bytes and compare a new Python reference to it (the same method as the ordinary-land rule, 0 mismatches over 21,214 cases).
- **Deposit amount and reserve flag (OQ-035 b/c):** not yet read; the survey shows every shipped salt ore object has amount 2,000 or 400 (`OCCUR` u16); the next reads are the deposit constructor's callers (island object creation from `OCCUR`) and `0x10078960`.
- **Constants read (2026-11-06).** `[0x10021780] = 1.0f`, `[0x100214ac] = 0.5f`: the cell size is `1.0 * 0.5 = 0.5` tile and the centring offset `0.5 * 0.5 = 0.25` tile, so the sample positions are the centres `(0.25 + 0.5 c, 0.25 + 0.5 r)` of the `2w x 2h` half-tile cells, taken in the rotation's order. The sampler `0x10008d90` reads the four byte vertices around the position (`byte[p]`, `[p+1]`, `[p+stride]`, `[p+stride+1]`, each scaled by the third argument 1.0) and finds the height by a ray/triangle intersection (`0x10015e90`, x87 float code with epsilon compares at `0x100213c8`): float behaviour that the simulation must not reimplement from reading alone; the contract is derived by comparison with the emulated original (section 11), with a deterministic integer formulation. (An earlier draft said heights are bytes in steps of 16; the evidence uses arbitrary bytes 0..255, since the helper does not assume steps of 16.)

## 11. X1 contract: the mountain-class terrain rule (class 0x3000; D + E; reference `tools/mine_terrain_ref.py`)
**Rule (original, `AnnoGame.dll 0x10008a80`, reached from the placement-compatibility function's `0x3000` arm at `0x100091a1`).** Inputs: the type's footprint bytes `w = type[6]`, `h = type[7]`, its HIGHMAP table (`2h` rows x `2w` columns of bytes, row-major, type `+0x234`), the vertex grid of the footprint window (`heights[z][x]` with `(W'+1) x (H'+1)` vertices, `(W',H') = (w,h)` for rotation 0 and 2, `(h,w)` for 1 and 3), the rotation 0..3, and the offset `lo` (the window's lowest cell minimum `& 0xf0`: the ordinary analysis' mode-2 result, flag word `0x3096 & 3 = 2`; only its low byte is used). For each table cell `(r, c)` take the sample point in quarter tiles
`rot 0: (1+2c, 1+2r)`, `rot 1: (1+2r, 4w-1-2c)`, `rot 2: (4w-1-2c, 4h-1-2r)`, `rot 3: (4h-1-2r, 1+2c)`;
the terrain height there is the triangle interpolation of the four vertices of the tile (`a b / c d`, diagonal `b-c`): `x4 = 2a+b+c` at (1,1), `2d+b+c` at (3,3), `b+3c` at (1,3), `3b+c` at (3,1) (quarter units, an exact integer; height = floor(x4 / 4) for byte heights). The site is **refused as soon as `table[r*2w+c] <= height - (offset & 0xff)`** (signed compare, so a negative difference always passes), otherwise accepted by the helper. The helper's acceptance is only one of the placement's conditions: the island function's step 7 additionally requires the result byte `lo >= 32` for any type whose PRODTYPE group is not `0x141` (MINE and STEINBRUCH are group 1) -- **this step-7 test is INHERITED from `tools/placement_ref.py` / `docs/re/ship-founding.md` 10.2 step 7 (its 32 threshold is the ordinary-land rule's) and was not re-derived for class 0x3000 here; the reviewer should treat it as inherited**, and every ordinary check (bounds, ownership, occupancy, payment, permission) still applies.
**Integer-only formulation.** The simulation needs no float: `x4` is an exact integer, the comparison is `table <= x4/4 - off` with floor division on non-negative values, and `lo` comes from the existing integer height analysis. No fixed-point approximation is introduced; the original's x87 ray/triangle code is *not* reproduced. Equality with the original sampler is established by the sweep below, and its limits are stated there.

## 12. X1 contract: the deposit (OQ-035 b/c; D; reference `deposit_load` in `tools/mine_terrain_ref.py`)
- **Which island objects are deposits (D).** The island-object factory (`AnnoWelt.dll 0x10094e00`) switches on the object type's BEWOHNTYPE: 145 `ERZSYMBOL` creates the deposit class (constructor `0x100637a0`), 146 `SCHATZ` the treasure class (`0x100637f0`). Load method (vtable `+0x64`, `0x100634e0`, run by the `OCCUR` reader `0x10095eb0` after creating the object): reads 8 bytes, `remaining = (u16 amount) << 8` (tons), the discovery mask to `+0x2c`; then, if the object's ware (`+0x84`) is an ore goods id in 1..8 and the flag is set and `remaining < 0x64000` (1,600 t), **`remaining` is reset to `0x7d000` (2,000 t)**. So the shipped 400 t salt ore (S01_04_01) loads as **2,000 t with the flag set**, a 2,000 t one stays 2,000 t, a 3,000 t one would stay 3,000 t. The flag is never cleared by the load. (Vectors `deposit ...`, all agreeing.)

- **Consequence for salt (D).** Salt mines are deep (every non-iron mine, `docs/re/production.md` 4.4). - **Edition setting.** `depletes` is world setting 14 bit 1 (add-on edition flag, OQ-035 a); the plan reads the existing `WorldSettings` field, not a new switch. For a flagged deep deposit it does not matter, which is why it cannot make salt finite.

## 17. X1 contract gap found while implementing X2: the flag-0x10 COVERAGE test applies to mines (2026-11-06)
**SUPERSEDED by section 18 (read it first).** The finding that the predicate exists stands; the polarity of its marking test, the "must sit on rocks" summary and every count in this section are corrected or void in section 18. Kept as history.
**Finding.** Implementing the class-0x3000 placement showed that the shipped mine types are refused by the engine's `classify` as `Other`/Unsupported not only for their class but because their flag word `0x3096` carries **bit 0x10**, the bit of the island function's *coverage test* (`AnnoWelt.dll 0x1007c955`-`0x1007cb3d`, `docs/re/ship-placement.md` "open" list, `ship-founding.md` 10.2 step 5). The X1 contract (sections 11-13) decoded only the terrain helper `0x10008a80` and **did not include this second predicate**; the contract therefore describes a necessary but not sufficient placement rule. A permissive implementation without it would invent a rule (forbidden: "an unread decisive predicate is remaining research"), so **no mountain placement is landed**; the work in progress is preserved on the local branch `wip/x2-mountain-without-coverage` (`f7ebe2ff`: window extraction, `site::mountain_helper_accepts`, `mine_source` bind/dedupe, `FigureType::ware` with its independent digest vectors, the C++ vector tests) and is explicitly NOT a candidate.
**What the code at `0x1007c955` does (read, disassembly; to be confirmed by emulation).** It runs when the type-flag/caller-flag argument has bit 0x10. For every tile of the footprint (`w = byte[esp+0x14]`, `h = byte[esp+0x15]` of the record, origin `x = u16[esp+0x10]`, `y = u16[esp+0x12]`) it takes the existing object id found under the tile in step 4 (a local word buffer); if the id is non-zero it asks the registry for that object's type (`+0x70`) and its flag word (type slot `+0x60`); **if that flag word has bit 0x10**, and the island tile record `[island+0xc][index*8 + 3]` has **bit 0x80 clear**, the tile marks its 8 x 8 chunk (index `(x/8 - x0/8) + (y/8 - y0/8) * 2` in a small byte array, `|= 1`). After the scan, every chunk the footprint overlaps (`(x0 + w + 7)/8 - x0/8` columns by the same for rows, rounding by the `cdq; and 7` idiom) must be marked, else the placement is refused (`0x1007cc08`). In words: **every 8 x 8 chunk touched by the mine's footprint must contain at least one footprint tile that already carries an overlay object of a coverage type (rock: `FELSEN`, `KLIPPE`, `STEIN`, ... flag words `0x12, 0x3a, 0x92, 0x8018`) whose tile byte-3 bit 7 is clear.** So a mine can only be placed over the mountain's rock objects, and the occupancy of such tiles is the *intended* overlap (the engine's `overlap_with_existing` already lets some rock types through; whether it matches this test is unverified).
**Consequences for the plan.** (1) The pilot site counts of section 15.1 (2,278 / 824 / 356) were computed **without** this test and are upper bounds; they must be recomputed. (2) The step-4 existing-object buffer (which tiles are listed, in which order, with what ids), the meaning and writers of tile byte 3 bit 7, and the exact chunk arithmetic for footprints that straddle chunk boundaries or lie at negative island-relative coordinates are **unread/unemulated**; the emulator (`tools/placement_emulate.py` runs the whole of `0x1007c790` on synthetic islands) must be extended with class `0x3000` types (HIGHMAP bytes), rock overlay objects of flag `0x10` and the tile byte, and the Python reference (`placement_ref.py`) gains the coverage rule, proved over random islands like the ordinary rule (0 mismatches), before any C++ lands. (3) The refusal matrix gets a *coverage* row (a terrain-legal, owned, free site with no rock under one of its chunks) with its legal neighbour. (4) The same bit is why the corpus check of section 11 (177/178 shipped placements accepted by the helper alone) says nothing about coverage: shipped mines sit on rocks by construction.

## 18. X1 addendum: the coverage predicate, decoded and emulated (2026-11-06)
**Correction of section 17's first reading.** The disassembly read in section 17 had the polarity of the marking test reversed. The rule that the original bytes implement (and that section 18's emulation fixes) is below. **The rule (`AnnoWelt.dll 0x1007c955`-`0x1007cb3d`, island function `0x1007c790`).** It runs when (type flag word | caller flags) has bit 0x10 (`0x1007c88e` ORs the type flag into the argument). Occupancy compatibility comes first (a rock of group 0x141 is compatible with a flag-0x10 placed type); the coverage test runs before the height analysis and also under the apply flag 0x1000000; flag 0x400000 skips both. Footprint `w`,`h` (at most 8 x 8), origin `x`,`y`:
1. For every footprint tile, the tile is **kept** iff it carries an existing object id != 0 whose type has flag 0x10 **and** whose tile byte 3 bit 7 (the anchor bit) is set. Every other tile (id 0, a type without 0x10, or a clear anchor) **marks** its world-aligned 8 x 8 chunk, index `(tx>>3 - x>>3) + 2*((ty>>3 - y>>3))`.
2. Every chunk the footprint touches (`rows = ((y+h+7)>>3) - (y>>3)`, `cols` likewise from x/w; mark array stride 2) must have a mark; otherwise the placement is refused (coverage reject, `0x1007cc08`). A chunk whose tiles are all kept is therefore refused; a chunk with no footprint tile marked cannot occur except through this case.
This is a **second, separate predicate** next to the terrain helper (`0x10008a80`, sections 11-13): a mine site must pass both. Coverage maps to `Reject::TerrainRefused` (no new reject code).
**Step 4 (who writes tile byte 3 bit 7), settled from existing evidence.** The sim's `TileLayer::foot_anchor` is written by `place_object_record` / original `0x10082040` on the first tile written per 8 x 8 block; the scenario loader (`scenario.cpp`) and `create_building` use it, so a loaded state carries anchors by the original rule. ## 21. X4: interruption, isolation, lifetime and timing boundaries (2026-11-06)
All on the pilot (endless02 island 1, city 0 of player 8) except the two-owner case (the pilot with a second city, below). Tests: `salt interruption X4: ...`, `salt lifetime X4: ...`, `salt timing X4: ...`, `salt isolation X4: ...` in `salt_placement_test.cpp`. No code in the engine changed for X4; the diagnostic `TransportStats` ledgers of X3 were enough.
**Low-stock setup (labelled fixture edit, every arm alike):** no preloaded SALZSTEIN and no SALZ in the city store, so the households can only buy what the chain delivers. **Windows:** 500 steps; phase 1 (1,000 steps) establishes the chain, phase 2 (4,000) runs interrupted, phase 3 (3,000) runs restored; the scoped ledger of X3, extended with history (what a removed mine or saltworks still held), closes (all residuals exactly zero) at the end of every phase.
**Interrupting each real link by public commands (observations, pinned):**
- *Mine* demolished: the saltworks drains its ore, then (last four windows of phase 2) nothing is made, unloaded, bought or delivered; rebuilt at the same site, production, receipts, purchases and deliveries all return (the deposit is the same object).
- *Road* (the 22 road tiles of the trunk and the stub beside mine and saltworks) cut: the same drain; rebuilt by `BuildCmd` of the same road pieces (all 22 accepted), the chain recovers.
- *Markets 1305 at (346,346) and (346,371)* (the homes of the carts that carry the SALZ to the store) demolished: the saltworks fills up and stops, nothing reaches the store, the households stop buying; the markets are **not restorable** by command (`ConstructionDenied`: the type is not buildable for the player), so the chain does not recover and the test pins exactly that.
- *Stalls 1310* (all four) demolished: production and receipts continue (the store fills), the households buy and receive nothing; rebuilt, purchases and deliveries resume.
- *Kontor 1306* (the warehouse) demolished: **no effect** on the chain. The city store belongs to the city and is reached by the markets' carts and the stalls, not through the Kontor building: "warehouse reach" is not a link of this model.
- *Households depend on renewed supply:* with an empty store, purchases (`taken`) and deliveries to houses are exactly zero for the last windows of every interruption that cuts production or receipt, and positive again after restoration, so it is not warehouse receipts alone.
**Lifetime boundaries (exact):** the saltworks demolished while its carrier holds ore: `ore lost == the cargo in the carrier's hands at that moment`; both markets demolished with SALZ in the carts: `SALZ lost == the carts' cargo`, nothing unloaded afterwards; the mine demolished while the carrier holds its ore: the cargo is delivered, nothing is lost. All close the ledger (lost cargo is history, not stock) and pass validate / save / load / continue. Two mines on one deposit: demolishing one leaves the other bound and working; the deposit (set to 321) is never refilled, by the teardown of both and a rebuild either.
**Timed-transition edges:** the demolition applied just before the step in which (a) a carrier lifts ore from the mine, (b) a cart unloads SALZ into the store, (c) a carrier arrives at the saltworks with ore: in each case the event does not happen in the demolished world, nothing is credited twice, the cargo in flight ends as history exactly once, and the ledger closes (the kept world's event happens, so the step is a real event step). Elapsed times: one tick is 2 ms and `advance(game_ms)` runs every subsystem once per call, **including `advance(0)`**, which adds no tick but changes the state hash and can draw from the existing per-call sites (FarmWorkerDispatch, HouseWalkerTarget, HouseVariant); 100 x 100 ms, 10,000 x 1 ms and a 0/1/99 mix reach the same tick and the same chain flow (works made, unloaded, taken) and keep the ledger closed, the same slicing reproduces the same bytes, but **different slicings give different states and PRNG cursors**: a recording must hold every advance's step (the host always uses the fixed step).
**Isolation (two owners):** the pilot with a second city (city 1, player 9) cut from our tiles, whose mine at (356,361), in reach of the same ore and nearer our saltworks than our mine at (359,369), and whose saltworks beside the same trunk road, work in the same run. Every load of the run (source, lifting figure's home) stays inside one city; our saltworks never lifts the rival's ore and the rival's never lifts ours; both ledgers close. A compiled mutant that drops the city filter of `Island::rect_query` makes loads cross cities and the test fails (killed). The rival's *activity* changes none of our flows: with its mine producing, bound and its saltworks standing, our flows equal those with its mine idle (source cut, no saltworks) exactly, and with its buildings demolished they equal the world with no rival buildings. What a standing rival building does change is *occupancy of the shared land*: our carriers' routes move a little (6,144 vs 6,104 units lifted), which is not a transfer between owners. **Ore is an island object**: both mines bind the one deposit (as in the original, where reach is geometric); only the output stores, lifts and credits are per city. Deposits are therefore shared across owners by design; a depleting edition setting (OQ-035 a) would let one owner's mine use the other's ore, which is *not* tested here.
**PRNG.** No new draw site and no draw added by any demolition, rebuild, payment or chain code. Households not live, demolish and rebuild at the same instant: the draws of every site and the final cursor equal the uninterrupted control (only *when* within the run a draw falls can shift, because the rebuilt buildings have new ids). Households not live, a link down for 4,000 steps: **only `FarmWorkerDispatch` differs from the control (e.g. 8,384 against 8,387 draws)**, from step 5,769 of 8,000; it is an existing site drawn once per eligible farm dispatch attempt. The mechanism is NOT established; a plausible one (unverified) is that the farms' outputs are lifted by the same markets' carts as the salt, so an idle chain changes farm state and eligibility. This is a count change at an existing site through shared state, not a changed draw order or a new site; it is reported here rather than hidden. Households live: `HouseWalkerTarget`, `HouseVariant` and `FarmWorkerDispatch` follow economy state (a payment-matched instant rebuild moves them too, X3), every other site is equal.
**Not covered:** a resident walker's cargo in flight when a stall is demolished (the walker carries it home regardless), repeated interruptions, other scenarios, depletion, and the depleting setting across owners.
