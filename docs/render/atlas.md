# Resident sprite atlases: what they cost, the layout, and the pages themselves (RENDER-DIRECT-1a/1b)

Task [`docs/orchestration/tasks/render-direct-1a.md`](../orchestration/tasks/render-direct-1a.md) (§1-8 below) and [`render-direct-1b.md`](../orchestration/tasks/render-direct-1b.md) (§9), [ADR 0007](../adr/0007-direct-rendering.md) step 1. Everything below is measured with the engine's own code (`bench_frame --atlas-report`/`--atlas-build`, `src/tools/bench_frame/main.cpp`), over the whole scene corpus, or marked as a choice. The budget and the mip level (§4, §7) went to the owner as a QUESTION and were decided 2026-11-17 (`docs/open-questions.md` OQ-096/OQ-096b); this page reflects that decision.

## 1. The command

`bench_frame <game_dir> <file> --atlas-report <out.tsv> [--atlas-gpu-limits]` (a mode of `bench_frame`, not a second tool: it reuses `load_any_scene`, `prepare_objects`, `animation`/`frame_index` and `AtlasResidency` directly, so there is no second implementation of scene loading, object preparation or packing to drift from the real one). `<file>` **"-"** walks the whole corpus (`<game_dir>/Scenes` recursively, plus the repo's `data/maps/lan5.txt` and the three `data/maps/candidates/ship-start-v2/*.json` candidates, resolved against the current working directory — run it from the repo root); any other `<file>` measures only that one scene, for a quick check. `--atlas-gpu-limits` additionally opens a real GPU device per adapter (step 6) — the orchestrator's go was asked for and given before this ran on the shared PC.

Decodes nothing it does not need: static and water frame sizes come from `formats::figuren::Frame::width`/`height` (file headers); only the figures a scene's units actually use are decoded (`scene.units`, already populated by `load_scene`), and only the whole-Anlagen.dat player-colour check (§5) decodes pixels, because that question is specifically about pixel content.

**Run** (M, native MSVC, `game/app` the shared game directory): 519 scenes (515 `.sze`/`.scp` under `Scenes/`, `lan5.txt`, 3 `ship-start-v2` candidates) in 7m12s wall, 0 refused. `--atlas-gpu-limits` (separately, one scene): the two GPUs below in a few more seconds.

## 2. Static and water frames, per scene and group

Columns measured per scene × group (0/1/2): distinct static frames and their bytes (dedup by `(ANLAGEN id, group, rotation-block step)`, `SpriteCache`'s own granularity), static *instances* (placed objects, not distinct frames — reuse is high: a scene can place the same building hundreds of times), distinct water frames/bytes (non-shadow and shadow counted separately), and the enhanced water's extra copies.

**Full animation, not one time sample (M, C).** A placed object's frame cycles through `frame_index`'s formula (`iso.cpp:350-357`): `step = (time_ms/ms + phase) % n` when `ms > 0` (animated: every residue 0..n-1 appears as time passes, independent of `phase`), or the single constant `phase % n` when `ms == 0` (no animation — one frame, not `n`). `bench_frame`'s `add_object_frames` enumerates exactly this set by calling the same public `animation()`/`frame_index()` functions `place_prepared` itself uses (iso.hpp), not a second implementation of the selection: this is why water objects contribute every frame of their cycle, and why a non-water entry that happens to carry real animation (`ms > 0`) is counted the same way — more complete than the superseded script, which only expanded animation for water.

**Enhanced water's extra copies (M, C).** `Scene::sprites_in` (`scene.cpp:927-932`) gives a water (not shadow) frame the smoothed variant only when style is `Enhanced`; `build_island_lists` (`scene.cpp:396-431`) excludes the surf sprite (`kSurfAnlage`) and river/waterfall pieces (`kRiverAnlagen`, `kRiverFallAnlagen`) from the enhanced lists — rivers become the procedural river surface and surf is drawn by the sea itself, so their frames are never doubled. `bench_frame` mirrors this exact exclusion (the same three constants, both public) to count only the frames that really get a second, smoothed copy; shadows never do (the smoothing only ever applies to non-shadow frames).

**Worst case across every page/padding/mip combination (M):** `Scenes/0010SingleEndlos/01_1024_easy_256.sze`, group 0 — 1,611 distinct static frames (101.9 MB) over 125,427 instances, 504 distinct water frames (77.7 MB, no shadows), 54 enhanced-water frames eligible for a smoothed copy (8.3 MB). One live ship (113 KB).

## 3. Packing: the shelf packer, four candidates, with and without a mip level

Packer: `anno::render::AtlasResidency` (`residency.hpp`/`.cpp`), the shelf packer `gpu-chunks.md` 4.2-4.3 already specifies and RENDER-DIRECT-1b is to build on — not a new one. One `ensure()` call packs the whole static+water set of a scene/group at once (budget sized so it never has to evict within that call), so the page count is a real packing result, not an area estimate; `ensure()`'s own tallest-first sort makes the layout independent of listing order (confirmed by the existing `residency_test.cpp` case). Four candidates: page size {2048, 4096} px, padding {2, 4} px added to every frame's width and height (both sides) before packing — the dilation ADR 0007 wants; whether 2 px is enough for 1c's actual dilation kernel is for 1b/1c to confirm, not measured here.

Mips do not change the page *count* (mip levels are generated by the GPU from the resident base page, not packed separately). **A full chain is not a usable candidate at this padding**: a mip level *n* needs 2ⁿ px of padding on every packed frame, or its atlas neighbours bleed into it when the GPU samples past the mip's own, shrunk edge; 2 px padding supports exactly one level (2¹ = 2 px), and a genuine chain down to 1×1 for a 2048 px page would need 11 levels — 2¹¹ = 2048 px of padding, absurd. The `mips` column's two values are therefore **none** and **one_level** (+25 % of the base, the exact cost of one half-resolution level: a quarter of the base area) — not "full"; a full chain is not listed because no padding candidate measured supports it (`src/tools/bench_frame/main.cpp`'s own `kOneMipLevelFactor` comment has the derivation). `pack_bytes` is base-or-one-level depending on the `mips` column; `rect_bytes` is always the un-mipped packed-rectangle total, for the fill ratio.

`01_1024_easy_256.sze` group 0, static + water combined, every candidate (M):

| page | pad | mips | pages | pack_bytes | rect_bytes | fill |
|---|---|---|---|---|---|---|
| 2048 | 2 | none | 12 | 192 MiB (201,326,592) | 180.0 MiB | 93.7 % |
| 2048 | 2 | one_level | 12 | 240 MiB (251,658,240) | 180.0 MiB | 93.7 % |
| 2048 | 4 | none | 13 | 208 MiB (218,103,808) | 189.0 MiB | 90.8 % |
| 2048 | 4 | one_level | 13 | 260 MiB (272,629,760) | 189.0 MiB | 90.8 % |
| 4096 | 2 | none | 3 | 192 MiB (201,326,592) | 180.0 MiB | 93.7 % |
| 4096 | 2 | one_level | 3 | 240 MiB (251,658,240) | 180.0 MiB | 93.7 % |
| 4096 | 4 | none | 4 | 256 MiB (268,435,456) | 189.0 MiB | 73.8 % |
| 4096 | 4 | one_level | 4 | 320 MiB (335,544,320) | 189.0 MiB | 73.8 % |

`fill` = rect_bytes / pack_bytes (un-mipped): how much of the allocated pages the packed rectangles actually cover; `1 - fill` is shelf waste, not a measurement error.

**The group mip ladder (why one level is most of the benefit).** The zoom groups themselves already form one: tile widths 84/42/20/10 px (`docs/app/window-trace.md` "Zoom groups and their tile widths"), never shrinking the finer set by much more than 2× (2.1× between groups 1 and 2, plus hysteresis) before the next group takes over. One half-resolution mip level covers nearly all of the minification a zoom between two adjacent groups needs; a second level would matter only right at a group switch, for a small added cost on top of what section 4 already finds tight.

**`scene.sum` rows (F1, groups together).** The same per-scene, per-group frame sets above are also summed, per scene, for **groups 0+1+2** (ADR 0007 decision 2: all three sets stay resident at once) and the adjacent pairs **0+1** and **1+2** (the pair a zoom between two groups needs held together, under the owner's seamless-zoom rule — no upload mid-zoom). Written by the same command run, same `page_size`/`padding_px`/`mips` columns, `group` holding the label instead of a number; the per-group descriptive columns (`static_frames` .. `figures_used_bytes`) are 0 on these rows since they are not meaningful summed. Section 4 uses them.

| group | frames | bytes | player-colourable frames | player-colourable bytes |
|---|---|---|---|---|
| 0 | 241,808 | 1,923.4 MiB (2,017,601,516) | 35,423 | 352.1 MiB (369,259,748) |
| 1 | 241,808 | 484.9 MiB (508,682,544) | 35,423 | 88.4 MiB (92,673,260) |
| 2 | 241,808 | 108.2 MiB (113,479,232) | 35,423 | 19.1 MiB (20,013,820) |

Group 0 alone is 1.9 GiB: **the direct path cannot keep the whole figure catalog resident** (ADR 0007's own premise).

**What `scene.units` can and cannot say.** `scene.units` (populated by `load_scene`, not by `load_placed_scene` — `lan5.txt` and the three `ship-start-v2` candidates are reported as 0 figures used for this reason, not because they truly have none) is the *scenario file's own starting* ships and soldiers only. A running game adds carriers, residents, animals and more ships as it plays, none of which `load_scene`/`scene.units` can see — the loader genuinely cannot tell how many figures a long game accumulates, so this section does not claim to measure that; the packet's own "otherwise say it cannot" applies here.

**The measured maximum of what is knowable from the start units** (deduplicated by `render::FrameKey::unit`, the frame table's own identity, across all 519 scenes × groups): **3,401,840 bytes (3.24 MiB), 74 frames, `Scenes/0201SingleAddOn/single38.sze` group 0.** This is the whole number this measurement can give; it is not a bound on a running game's figure residency need, which is unmeasured. Figures are **not included in the static+water packing** in §3-4 — ADR 0007's own figures/hot class is a separate, **evicting** residency budget (`gpu-chunks.md` 4.2's Static/Hot split, the same split §7 recommends for buildings/water vs. figures), sized later from a running game, not from the start units alone.

## 6. Player colours

**Static (Anlagen.dat) frames: structurally never recoloured (M, C), and a real finding about their pixel content anyway.**

- `anno::render::SpriteCache::get` (`iso.hpp:276-277`) — the only place that decodes a static frame for drawing — has no colour parameter at all; it calls `assets::building::to_rgba(anlagen, entry, group, frame)` (`iso.cpp:322`), which also has no colour parameter (`building.hpp`). `assets::figure::player_coloured`/`recolour` are called only from `assets/src/unit.cpp` (lines 180, 207), the live-unit path, never from `iso.cpp`'s static draw path. So today, 0 static frames carry a player colour — this is the engine's current behaviour, not a property of the files.
- **Decoded anyway, and this is not a player-colour signal.** `bench_frame`'s `static_player_colour_eligibility` decodes every static frame (`assets::building::to_rgba`, the same function `SpriteCache::get` calls) and tests each covered pixel against `figure::recolour`'s own test (`G² > trunc(1.5·(R² + B²))`, green dominance — applied by comparing the decoded colour against `recolour(colour, test_player)` rather than reimplementing the formula): **11,180 of 27,537 non-shadow frames (40.6 %)** have at least one matching pixel, **3,760,786 of 102,530,209 checked pixels (3.67 %)**. That test is a green-dominance test, and building frames are full of ordinary green — grass, trees, fields, painted parts of textures and sprites — so this result shows only that **the decoder's green-dominance test cannot be applied to static frames to find player colour**: it matches ordinary scenery just as readily as any marked colour would, and nothing distinguishes the two from this measurement. It is **not** a finding that a meaningful share of building pixels "would be recoloured" in any useful sense, and not a look-and-feel question for the owner to pick a default for — there is no marking here to turn on or off.
- **A real, separate open question (OQ-690):** whether the *original* ever draws any static object (a flag, for instance) tinted by its owner's colour at all, through a different mechanism than this test can see. OQ-022 already found that the Anlagen.dat COLORS `flag` value 4 means `EffectsMulti`, a player-colour-variant palette kind, used by colour table id 109, `Flagge01_01.PCX` — a flag. Whether any *placed* ANLAGEN object actually uses that table, and whether the original renders it recoloured, is unresolved and out of this task's scope; `docs/open-questions.md` OQ-690 names it for RE or a capture of a placed flag object across players.

**Figures: 69 of 368 FigurenHeader.dat entries** (17 BEWOHNTYPE names, `figure.hpp`'s own `kPlayerColouredTypes`), 35,423 of 241,808 frames at group 0 (section 5's table; ships are not among the coloured types). Each decoded, coloured copy is a separate `SpriteKey`/`FrameKey` (variant folds the colour into the key), so holding every colour used is literally one decoded image per (frame, colour) pair.

**Two ways to hold a figure's player colour (measured bytes of each, not chosen for the owner; both rest on the scenario's *start* units only, §5 — not a running game's full figure population):**
1. **One decoded copy per colour a scene uses.** Bytes = (player-colourable bytes the scenario's start units need) × (distinct colours the scene's players use, up to 8 in the original). Against the measured maximum start-unit need (§5, 3.24 MiB, one colour): at up to 8 colours, ≈ 26 MiB — a figure-class cost, not part of the static+water budget §4 checks.
2. **One uncoloured copy plus a mask, coloured per instance** (T11 section 10 item 3): bytes = the player-colourable bytes the start units need, once, regardless of how many colours are in play, with the colour applied at draw time (a shader uniform per instance, not a GPU-memory cost measured here).

A performance/complexity trade-off (one atlas entry per colour vs. a per-instance shader parameter), not obviously a memory one at the start-unit scale measured — but §5's own point stands: a running game's figure population, and so its real player-colour cost, is unmeasured here. Not decided — the owner's call, once the figure class's own budget (§5) is sized.

## 9. The pages themselves (RENDER-DIRECT-1b)

Section 7's layout as real bytes: `anno::render::build_atlas_pages` (`src/render/include/anno/render/atlas_pages.hpp`, `src/render/src/atlas_pages.cpp`) builds the page buffers `AtlasResidency` only sized in §1-8 (reusing `AtlasResidency::ensure`/`place` for the actual packing, not a second packer), on the CPU — nothing here is read by any render path yet (RENDER-DIRECT-1c uploads and draws from these pages). `anno_render`/`anno_render_tests` (CPU-only, no `wgpu` dependency); the one piece that needs the adapter type (the budget default, below) lives in `anno_render_gpu` instead, but is itself pure arithmetic, tested with no GPU device opened.

**The byte format.** Each page is `page_size`² RGBA8 texels at level 0, `(page_size/2)`² at one mip level, zero-initialized outside every placed frame's slot (`AtlasPages::level0`/`level1`, `atlas_pages.hpp`). A frame's slot is `2·padding` texels larger than the frame in each dimension (padding on every side), the frame itself at the slot's `(padding, padding)` offset (`write_level0`, `atlas_pages.cpp:50-61`) — the layout §3/§7 already chose (2048 px pages, 2 px padding), now actually built rather than only sized.

**Premultiplied alpha.** `premultiply_pixel` (`atlas_pages.hpp:67-74`): `c' = (c·a + 127) / 255` per colour channel, integer, half up; alpha unchanged. No existing integer premultiply rounding rule was found elsewhere in the codebase to reuse instead — `sea::unpremultiply` (`render/src/sea.cpp:823`) is the only other premultiply-related code, float-valued, and the reverse operation (unpremultiplying for display, not premultiplying for storage).

**Dilated padding.** Every slot texel outside the frame's own rect is filled from the *nearest frame texel, clamped to the frame's edge*, premultiplied the same way as the frame's own content (`premultiplied_clamped`, `atlas_pages.cpp:34-44`, used by `write_level0`): a renderer sampling slightly outside the frame (bilinear filtering near an edge, or the mip's own 2×2 box reading one slot-local texel past the frame) reads the edge colour repeated, not the next frame's unrelated pixels or a hard zero.

**The one mip level.** `write_level1` (`atlas_pages.cpp:67-86`): each level-1 texel is the 2×2 box of level 0 below it, summed per channel and rounded half up, `(s + 2) / 4` — a box filter, not a float average, matching the "integer math only" convention `sim`/`render` CPU paths already follow. **Why this is safe to build with no shared lock on the per-texel path (step 3):** every slot's width and height are rounded up to the next even number before packing (`round_up_even`, `atlas_pages.cpp:14-16`); since the shelf packer places slots edge-to-edge starting from `(0, 0)` and a sum of even numbers (including 0) is even, every slot's own origin is therefore also even — so the page-wide 2×2 mip grid never has to average texels from two different frames' slots at a boundary. A naive per-slot-local mip grid would risk exactly that for an odd-sized frame; this is a reasoned invariant, not an untested assumption, and the dilation already absorbs the one extra texel the rounding can add.

**Built in parallel, proven thread-independent.** `build_atlas_pages`'s worker lambda (`atlas_pages.cpp:142-163`) splits the placed frames evenly across `threads` workers; each worker only ever writes its own frames' own slots (into level 0, then level 1, both already allocated to their final size before any worker starts), so there is no shared mutable state on the per-texel path. Packing itself (`AtlasResidency::ensure`, one call) stays single-threaded — only the per-frame texel work is split. Not just asserted: `atlas_pages_test.cpp`'s thread-count-independence case hashes the built pages (FNV-1a) at 1 and at several worker counts on the same frame set and checks the hashes are equal.

**The budget default, as a pure function.** `atlas_budget_bytes_before_sprite(atlas_budget_mb, adapter_type, max_layers, layer_bytes)` (`src/render/include/anno/render/gpu.hpp`) extracts `cb_atlas_budget_bytes`'s own default-selection and clamp logic (`gpu.cpp`) into a function that needs no GPU device to call: 512 MiB discrete / 384 MiB otherwise (OQ-096/OQ-096b, §4) when `atlas_budget_mb` is unset, the explicit value otherwise, both clamped to `max_layers · layer_bytes`. Tested in `gpu_test.cpp` ("atlas_budget_bytes_before_sprite: the default, the override and the layer clamp...", 9 assertions) without opening a real adapter — `anno_render_gpu_tests`' other cases still need one, but this one does not, so it needs no GPU coordination to run.

**The texel-exact proof (step 4).** Two kinds of check, both against the real decoder, not a second implementation of it:

- **Synthetic** (`atlas_pages_test.cpp`, no game files): a 1×1 frame, odd sizes (dilation must not read past the frame on either axis), a frame sized to exactly fill a page, alpha 0 and 255 at the frame's edges (premultiply must not corrupt either extreme), the thread-independence hash case above, an oversized-frame case (reported in `AtlasPages::oversized`, not silently dropped), a duplicated-frame-id case (reported in `AtlasPages::duplicate_ids`, placed once, hash-equal at 1 and N threads — review F3), and a case asserting `mip_x`/`mip_y`/`mip_width`/`mip_height` against the slot-origin floor/ceil formula directly on an even- and an odd-sized frame (review F4). 8 `TEST_CASE`s, **120/120 assertions** (native MSVC Release).

## 11. The upload (RENDER-DIRECT-1c)

**The unit.** `src/render/include/anno/render/atlas_upload.hpp` / `src/render/src/atlas_upload.cpp` (new, `anno_render_gpu`): a standalone module that opens no device of its own (the caller's `gpu::Context`) and touches no `GpuFrame` state. `upload_atlas_pages(ctx, pages, budget_bytes)` makes one 2D texture array, `page_size` x `page_size` x `pages.level0.size()` layers, **RGBA8Unorm, 2 mip levels** - the same format family the existing sprite atlas uses (`new_atlas`, `gpu.cpp`), never the `*Srgb` variant (`GpuFrame::create`'s own "a sRGB target would convert twice" rule applies equally here: the pages hold colours as written, no conversion on upload). Level 0 and the one mip level `build_atlas_pages` already built on the CPU are each written with their own `queue.writeTexture` call per layer (no GPU-generated mips: the CPU's own box filter is the one under test, RENDER-DIRECT-1b; letting the GPU regenerate a mip would silently redo it, untested against it). Usage is `TextureBinding | CopyDst | CopySrc` (`CopySrc` for the readback proof).

**The refusal**, named not truncated: `atlas_upload_refusal(layers, page_size, max_array_layers, max_dimension_2d, needed_bytes, budget_bytes)` is a pure function (no device) checked against three conditions in order - no layers at all, the layer count over the device's `maxTextureArrayLayers`, the page size over its `maxTextureDimension2D`, or `atlas_pages_bytes(pages)` (level 0 plus the one mip level, per layer) over `budget_bytes`. `upload_atlas_pages` reads the real device's limits (`wgpuDeviceGetLimits`) and calls this function for the decision, so the decision itself is unit-tested with no GPU at all (the packet's own acceptance item) while the device-reading wrapper is exercised by the GPU cases below. `budget_bytes` is the caller's own `atlas_budget_bytes_before_sprite(...)` minus the existing sprite atlas's current footprint (`cb_atlas_budget_bytes`, gpu.cpp) - this unit holds no `GpuFrame` state to subtract from, so it takes the number, not the subtraction, from the caller (there is no caller yet: the draw passes that will call this are stages 2-3).

**Which groups: `resident_atlas_groups(adapter_type, zoom_group, group_count)`.** A pure, total function (§7's own "adjacent pair" language, OQ-096/OQ-096b): a discrete adapter's result is every one of `group_count` groups (ADR 0007 decision 2 - ignores `zoom_group`, since the 4090 holds everything at once regardless of where the zoom is). Any other adapter's result is the two-element pair `{zoom_group, zoom_group + 1}` - `zoom_group` names the group the picture is **currently composed on** (`docs/render/iso.md` "Choosing the level": the coarsest level whose tile width is at least the zoom), clamped to `group_count - 2` at the top of the range (a zoom "at" the last group is still between the last two groups, not past them), and a single group when `group_count <= 1` (no pair exists).

**Why the coarser neighbour, `zoom_group + 1`, and never the finer one, `zoom_group - 1`.** This is this task's own choice (OQ-096/OQ-096b did not spell it out further), named here as the packet's review asked, and it follows from "Choosing the level" itself rather than from a direction or a last-step heuristic: while the picture composes on group g, the scale `zoom_now / tile_w(g)` stays in `(0.95 * max_upscale / ratio(g), max_upscale]` - at most 1 (`max_upscale` = 1 at the defaults), with the **lower** bound set by the hysteresis against the *next coarser* level's own switch-in point (the 5 % hysteresis is on the coarse side only). Converting that bound by the ratio between levels (`tile_w(g) / tile_w(g + 1)`, about 2 or 2.1) puts `zoom_now` just above `tile_w(g + 1)` - so **whenever the picture is shown on group g, the continuous zoom position is always between `tile_w(g)` and `tile_w(g + 1)`, never between `tile_w(g)` and `tile_w(g - 1)`**: that second interval is exactly where the picture has already switched to being shown on `g - 1` instead (the scale on `g` there would exceed `max_upscale`, which `zoom_level_for` does not allow at rest). So `g + 1` is not an arbitrary pick between two equally plausible neighbours; it is the only neighbour the zoom can be adjacent to while `g` is the group shown. (This also means the pair's membership changes only at a group switch, which already carries its own hysteresis against flapping - the resident pair does not need a separate one.) `resident_atlas_groups` itself is tested without a GPU, for discrete/integrated/CPU/unknown adapter kinds and `group_count` in {0, 1, 2, 3}, including the clamp at the top of the range.

**The placement-to-UV rule: `sample_placement`, realized as `textureLoad`, not a sampler.** Every other pass in `gpu.wgsl` reads a resident texture with `textureLoad` only ("textureLoad, never filtered, so cached chunks and sprites stay exact", `gpu.wgsl`'s own comment) - no `WGPUSampler` object exists anywhere in this codebase yet. RENDER-DIRECT-1c follows that convention rather than introducing the first one: the new shader `src/render/shaders/atlas_upload.wgsl` (its own module, not a change to `gpu.wgsl` - "a new unit, not a change to the chunk compositor") draws one full-target triangle (`scale_vs`'s own trick) and its fragment shader computes `textureLoad(atlas_tex, origin + floor(pos.xy), layer, level)` - the destination pixel's own integer index added to the placement's origin, exact at every texel, no rounding to get wrong. This is strictly the "nearest sampler, UVs at texel centres" rule the packet asks for, with the ambiguity a true sampler could introduce at a rectangle's edge removed by construction rather than by choosing the rounding carefully; `placement_to_UV` is realized as this one function (`sample_placement`, C++) plus the one WGSL entry point, both new, both shared - a later draw pass calls `sample_placement`'s own shader module (`shaders::atlas_upload()`) rather than re-deriving the mapping.

**Readback (step 2) and sampling (step 3): both proofs, both adapters.** `read_back_level(ctx, tex, layer, level)` copies one layer's one mip level back (texture-to-buffer, `mapAsync`, the row padding of the copy stripped - `GpuFrame::read_back`'s own pattern, copied here since this unit holds no `GpuFrame` to call it on) and is compared byte for byte (`std::vector<std::uint8_t>::operator==`) against `AtlasPages::level0[layer]` / `level1[layer]`; `sample_placement(ctx, tex, place, level)` draws one placement's own rectangle (or its mip rectangle) into a new, exactly sized offscreen target and is compared the same way against the matching sub-rectangle of the same CPU page. Both ran, both exact, on **both of this PC's adapters** (`ANNO_GPU_ADAPTER=RTX` / the Radeon iGPU selected by name, `play_gpu_test.cpp`'s own pattern - a Radeon run is a Radeon result, never the RTX default), on:

## 13. The Radeon's real allocation ceiling, measured and diagnosed, not fixed (RENDER-DIRECT-1d)

RENDER-DIRECT-1c review F1/F2 found that `endless02.sze`'s real resident pair (356,515,840 bytes) fits the calculated Radeon budget (402,653,184 bytes, sprite atlas taken as 0) but the real device refuses the single 17-layer texture allocation anyway ("Not enough memory left"). RENDER-DIRECT-1d answers why, measurement and diagnosis only - no production code changed, OQ-096b's 384 MiB default NOT touched (`src/render/tests/adapter_memory_diag_test.cpp`, new, `anno_render_gpu_tests`).

**Question 1: a single-resource ceiling, not the heap's own capacity - but a small one.** `endless02.sze`'s pair uploaded as two SEPARATE per-group textures instead of one combined texture: group 1 (4 layers, 83,886,080 bytes/80.0 MiB) allocated; group 0 (14 layers, 293,601,280 bytes/280.0 MiB) was refused even on its own, split from group 1. This confirms the real limit is a per-resource allocation ceiling (splitting helps in general), but the ceiling itself is small enough that even ONE of this scene's two groups alone can exceed it - splitting a resident set into exactly as many textures as there are zoom groups is not always sufficient.

**Question 2: DXGI's own memory facts (`DXGI_ADAPTER_DESC`, `IDXGIAdapter1::GetDesc1`, matched to the already-opened wgpu adapter by `vendorID`/`deviceID` from `wgpuAdapterGetInfo` - `WGPUAdapterInfo`, webgpu.h, has no memory-size fields at all to read directly).**

| Adapter | DedicatedVideoMemory | DedicatedSystemMemory | SharedSystemMemory |
|---|---|---|---|
| RTX 4090 | 25,310,527,488 B (24,138.0 MiB) | 0 | 16,704,471,040 B (15,930.6 MiB) |
| Radeon iGPU | 488,390,656 B (465.8 MiB) | 0 | 16,704,471,040 B (15,930.6 MiB, same shared pool - expected for an integrated part) |

**Question 3: the real single-resource ceiling, found by bisecting the layer count of a single 2048×2048 texture array (`layers_allocate`, binary search through `upload_atlas_pages`'s own error scope, RENDER-DIRECT-1c's fix) on the Radeon: 12 layers (251,658,240 bytes, 240.0 MiB) allocate; 13 layers (272,629,760 bytes, 260.0 MiB) are refused.** This is consistent with question 1's finding (group 1 at 80.0 MiB is well under; group 0 at 280.0 MiB is well over) and is **about 52% of the 465.8 MiB `DedicatedVideoMemory`** DXGI reports (question 2) - a real allocator-level restriction below the adapter's own reported dedicated VRAM, not simply "the dedicated VRAM is smaller than the budget." All numbers measured on this PC's specific Radeon/driver/Vulkan combination on 2026-11-17; the bisection *method* is reusable on other hardware, the specific 240 MiB figure may not be.

**For the owner (not decided here - OQ-691, `docs/open-questions.md`): OQ-096b's 384 MiB non-discrete default is well above the real ~240 MiB single-resource ceiling found on this adapter.** Three non-exclusive options prepared, none implemented: (a) lower the non-discrete default below the real per-resource ceiling (with some safety margin, and possibly measured rather than hardcoded, since it is driver/hardware-specific); (b) split any resident set above a configured per-resource size into more than one texture at upload time (a stage 2/3 design question, unrelated to the *total* budget number); (c) measure the real ceiling at runtime per-adapter (bisect once, cache) instead of guessing a number that may not transfer to other Radeon iGPUs or driver versions.
