## Reproduced defects

### [P2] Stamp the current velocity, not a normalized heading — src/sim/src/ship_mover.cpp:64

`RegistryShips` supplies +/-1 or +/-0.7071 as `LocalShip`'s direction. The
consumer multiplies it by 25. The traced original's slot +0x60 returns unit
+0x20: the current segment's **velocity**, already multiplied by speed and the
segment factor (RE sections 7.2, 7.3 and 9.4). A type-1502 ship at x=5340/256,
speed_q32=154618816 and factor=100 is stamped at tile **45** by the actual
adapter; `trunc(x + 25 * velocity)` gives tile **21**. A small open-water query
then selects endpoint (21,64) with the current stamp versus (20,66) with the
velocity stamp. This affects existing planning-only congestion, even though
local collision avoidance remains deferred. Correct the units throughout the
adapter/interface/reference and test actual moving-world data, including
cargo/health factors, diagonal and stationary segments. The current header's
unit-direction definition and helper tests encode the same wrong interpretation.

### [P2] Preserve authoritative motion when carrying a navigating figure — src/sim/src/scheduler.cpp:145

A valid scenario may parent a navigating figure to another ship. Scenario
creation initializes its `NavMotion`, but the carrier's `FigureMove` updates
only its published `Figure::pos`. The fine accumulator remains at the old
position; the scheduler also independently visits embarked navigating figures.
A public `World::create` / `MoveCmd` / `advance` reproducer needs only a ship,
11 unrelated plain figures and a navigating child of the ship. At Advance 11,
both published x coordinates are 5340, but invariants fail with
`Figure::pos does not equal floor(pos_u) on axis 0`; `World::load(w.save())`
rejects the same state. Define and enforce one carried-motion policy, keep the
fine position and published position coherent, and suppress independent
embarked sailing. A command refusal for an embarked ship alone does not solve it.

### [P2] Carry the whole validated descendant tree — src/sim/src/ship_mover.cpp:256

The mirror walks at most eight parent edges. The accepted parent-graph contract
has no such depth limit, and previously validated deep chains are still legal.
With one ship followed by nine nested plain figures, creation succeeds; at
Advance 11 the ship is at x=5340 while the ninth descendant remains at x=5248.
The existing two-level scout/donkey case cannot detect this. Traverse the actual
carried subtree with bounded iterative work and a derived child index, rather
than silently truncating an otherwise valid graph or adding an arbitrary depth
limit to make the test pass.

## Requirements still open, not waived by review

These are disclosed implementation choices or missing evidence, separate from
unintentional defects above. Reviewer approval cannot authorize dropping them.

- **Object-aware routing:** MAP-NAV-2 A3/C1 required the evidenced object
  predicate and invalidation. `RouteCache` instead disables objects. Autonomous
  scenery changes expose a cache-invalidation problem; ignoring the objects
  changes game rules and is not an approved solution. The placed-item base
  height is also absent. Restore the evidenced data path and update derived
  data for relevant command and autonomous changes. The current regression
  `route cache: it ignores placed objects ...` only proves both paths ignore
  the same input; it is not proof of faithful, history-independent routing.
- **Local work and scale:** C3/F3 explicitly required production locality and
  larger-content measurements. Admission scans all figures per attempt;
  `RegistryShips` scans all figures per plan and all collected ships per cell;
  crew mirroring scans all figures per moved ship. `WorldTileSource::entry_at`
  also scans island entries for an unindexed/open-sea cell. The helper's
  `ships_examined` counter excludes work hidden in its adapter. Measurements
  around twenty figures do not establish the required scaling. Measure and
  remove unnecessary dependence on unrelated content without changing fair
  admission or introducing nondeterministic scheduling.
- **Health-speed input:** B1/D1 required the health term. The implementation
  always uses full health although it loads `max_hp`. Carry and validate the
  minimal health state/input needed for the evidenced formula, default new
  expeditions appropriately, and test damaged ships and persistence. This does
  not authorize combat, damage commands, sinking or healing systems.
- **Populated navigation serialization oracle:** the Python updates cover
  default rules/counters and type facts, not a populated `NavMotion`. The ledger
  acknowledges this. Add a small independent byte transcription of populated
  moving and waiting states, including carry and tickets. A C++ writer/reader
  round trip cannot alone detect a common omission.

## Closeout decisions

1. Preserve the proven command, fairness, route, integer stepper and canary work.
   Complete MAP-NAV-3 in the task board; no broad rewrite or research restart.
2. Object blocking, health speed and production locality remain required.
   Documenting an omission does not complete its requirement. Use data-driven
   original defaults and validated mod inputs; do not hardcode the five-ship
   setup, eight descendant levels, player 0 or type 1502.
3. Existing explicitly approved adaptations remain: authenticated issuer,
   deterministic integer motion/persistence, bounded serial fair planning,
   atomic refusal and later failed-route events. Local detours and hostile
   avoidance remain deferred, with overlap disclosed. Peace alone is not a
   fidelity justification for omitting friendly collisions.
4. Keep unaligned shore-band/original world-edge questions and original-runtime
   captures open with precise scope. Do not invent original behavior to close
   them. Required robust bounds and deterministic supported-world behavior still
   apply. No Windows rendering assignment is expanded by this review.
5. Regressions must use production callers and distinguish the old wrong data
   adapter. One focused counterexample per invariant is enough; there is no
   mutation-count quota or added full review cycle. Use the already required
   package reviews and one final integration review, fixing actionable P2s as
   well as P1s before completion.
6. No merge or task-code push is authorized here. Freeze the next corrected
   headless candidate for orchestrator review; target-host gates remain separate.
