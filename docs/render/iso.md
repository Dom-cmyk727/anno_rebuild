# Isometric projection (island view)

**Status:** draft — rules derived from sprite measurements, visual checks and static analysis of the original ([`docs/re/annodisplay.md`](../re/annodisplay.md), [`docs/re/annowelt.md`](../re/annowelt.md)); not yet compared with screenshots of the original. Open points in OQ-026.

The original renders differently in structure: ground is a mesh of Gouraud-shaded, depth-buffered textured triangles, and sprites are depth-tested per pixel (`z` bytes are depth offsets). This renderer is a painter's-algorithm approximation that uses the same projection constants.

Implementation: `anno_render::iso` (CPU reference renderer), `anno_render::scene` (scenario composition), `anno-extract view`, `anno1503 --view`.

## Elevation
- `HEIGHT[x, y]` is the height of tile corner `(x, y)`; tile `(x, y)` spans corners `(x, y)`, `(x+1, y)`, `(x, y+1)`, `(x+1, y+1)` (D: `AnnoWelt.dll` corner grid with stride width + 1, `0x100900c0`, `0x10084870`; the corner reading of `HEIGHT[x, y]` is likely). Each tile is two triangles split along the fixed diagonal from corner `(x, y+1)` to `(x+1, y)` (D: `AnnoWelt.dll` `0x1009b920`, indices A,B,C and C,B,D); the renderer interpolates height inside each triangle. The original also shades each corner from the terrain normal (D: `0x100a03c0`, light vector not traced) — not reproduced.
- One height unit = 0.04 world units (D: `AnnoWelt.dll` table `0x100E35E0`); one world unit up = 51.477 px at zoom group 0 (D: `AnnoFrame.dll` camera `0x10071d70`: scale 59.1633, tilt 29.53°). `iso::HEIGHT_LIFT` = 2.059 px per unit at group 0 (scaled by tile width for groups 1, 2). The same camera gives 83.67 × 41.24 px per tile at zoom 0, consistent with the 84 × 42 sprites.
- Flat raised tiles (tried first) produce terraces and gaps; per-corner slopes remove them (visual).
- Rasterisation (implementation): each triangle is filled in screen space, every pixel centre inside it once (small edge tolerance so shared edges leave no cracks), with the texture position interpolated from the corners (a planar triangle projects affinely, so this is exact). Replaced an oversampled forward mapping on 2026-10-17: a 1920 × 1080 view went from 477 ms to 25 ms.
- Open water (texture 0) and textures 1–10 are not part of the original's terrain mesh (D: `AnnoWelt.dll` `0x1009b920`).

## Animation and layers
- A sprite set's `ANIM` record gives the animation: bytes 2–3 frames per animation, bytes 4–5 milliseconds per frame (bit 25 of the `u32` at 4 is a flag of unknown meaning). Frames per set = animation frames × 1 or × 4 rotations (P, all sets). Frame shown = `rotation · frames + (time / ms + phase) mod frames`; phase = the item's phase bits (surf: `(3y + 5x) mod 32`), `(5x + 3y) mod 32` for the sea. The original divides its tick by `ms / 2` (D: `0x100a03c0`); the tick unit is not traced, so the renderer uses the `ANIM` ms per frame (possibly half the original speed).
- Only the water layer (sea, rivers, waterfalls, surf) is animated so far; other animated objects (e.g. mills, fires) show their first frame.
- Layers (`scene::Layers`), in order: ground; water objects below sea level; the sea surface (whole region); water objects at or above sea level; other objects. Ground and objects are static per zoom group.
- Frame pipeline (`anno_render::frame`, used by the viewer and the benchmark): static data (ground, objects, the per-pixel sea field `sea::WaterField`) is built per 512 × 512 px chunk by background workers and cached. The workers take jobs from a priority list that every frame rewrites (visible chunks, then a ring of one chunk around the view, then the same area in the neighbouring zoom groups); a chunk not built yet shows open sea. A frame then composes ground → water objects below sea level (at the frame time) → sea (per-pixel lookup into `sea::SeaPattern`, the periodic sea image of each animation step, rendered once per zoom group) → water objects above sea level → objects.
- Two compositors with the same rules: the GPU (`anno_render::gpu`, wgpu, shader `gpu.wgsl`; chunks as textures, sea pattern as texture arrays, water objects from a sprite atlas, two render passes) and the CPU (`FrameRenderer::render`, row bands on all cores). Integer pixel positions and `textureLoad` keep the GPU exact: identical to the CPU within 1 per channel for the original water (`bench_frame --check`). Measurements: [`docs/perf/README.md`](../perf/README.md).
- The viewer uses the GPU when available (`--renderer auto|gpu|cpu`), presents with vsync and shows the renderer and frames per second in the title; while the window is occluded it retries every 100 ms instead of spinning. The CPU fallback redraws at the display refresh rate. `Original` water changes image once per 50 ms animation step, as the sprite's `ANIM` record; `Enhanced` cross-fades between consecutive steps.
- Shadows are 37.5 % black drawn over the destination (= 5/8 brightness on opaque pixels), so they also work on a transparent object layer.

## Reference: gameplay video of the original (2026-10-17)
Source: YouTube video `2I-T_8SAFuU` (Anno 1503 History Edition — the 2020 re-release of the same engine and data; differences from GOG 2.0.0.5 are possible), 7:50–12:00 at 1920 × 1080, analysed locally; no frames are kept in the repository.
- **No breaking waves.** Coasts go from sand to translucent shallow water (sea floor visible, lighter near the shore) to deep blue; no foam lines on beaches, only a ship's wake. Confirms that the faithful water has no breakers and that `WaterStyle::Enhanced` is an addition.
- **Water animates:** in a static camera shot, water pixels change ≈ 4 × as much as land pixels between frames 0.2 s apart (land change = compression noise).
- **Loop period ≈ 0.8 s:** frame-to-frame difference of a water patch is smallest at 24 video frames (0.8 s at 30 fps) and largest around 12–16 frames. That matches 16 frames × 50 ms from the sea sprite's `ANIM` record, i.e. one animation step per `ANIM` ms, and rules out the double speed (0.4 s) that `tick / (ms / 2)` with a millisecond tick would give (OQ-026).
- **Colour:** open sea averages RGB (28, 89, 138) in the video, ours (37, 107, 142) at zoom 0 — the original is darker and less green. Candidate cause: the colour parameter `0xC0` passed with every water sprite (selects a colour-table variant, not applied yet; `docs/re/annodisplay.md`). The original's water texture also looks finer and more sparkling.

## Enhanced water (not in the original, opt-in)
Off by default; `E` in the viewer, `--water enhanced` for `--png`. Applies to sea pixels only, so cached ground and objects are unaffected. Not derived from the original (which has no breakers, see "Reference"); the owner's target is crashing waves on coasts and open sea (PLAN §0.2). Tuning lives in `iso::Waves::DEFAULT` (to become configuration); `gpu.wgsl` mirrors it.

Reworked 2026-10-17 after the colleague's review recording, which showed white blobs forming a dash pattern at zoom group 2 ("Rasterstreifen"), thin lines parallel to the coast, angular coastal bands and a muddy shallow band. Current model (`iso::wave_shade` → light, foam, tint):
- Open water: slow swell from two drifting layers of smooth value noise (brightness ± 7 %); no whitecaps.
- Waves on every side (revised again 2026-10-17, owner: "waves are only rendered along one axis"): two wave systems blended by **amplitude**, the common approach for shoreline waves: an open-sea swell from one direction, and near the coast (within ≈ 3 tiles, `ws` = smoothstep over the smoothed shore distance) a surf system whose crests are lines of equal shore distance (`dist / 1.8 tiles + t / T`), so they run parallel to the shore and travel towards it on every side of an island. Blending the two phases instead compresses crests into bunches of thin lines; blending their crest profiles does not. Breaking, foam and swash use the blended crest; swash follows the surf system.
- Rivers (enhanced, 2026-10-17 after owner feedback "edges way too sharp, unnatural"): the depth-tested sprites keep the hard, triangle-shaped cut of the terrain and the overlapping 3 × 3 pieces show as patches. Enhanced water therefore draws river pieces (`scene::RIVER_ANLAGEN` 2701, 2705–2707) itself, like the sea coast: a river surface level per height corner (item height + 9, `sea::RIVER_LEVEL`; averaged where pieces overlap, smoothed twice and spread one corner), water where the river bed lies below it, with a soft edge (bed = `sea::river_bed_height`, an interpolating Catmull-Rom surface, not `smooth_height`, and never narrower than the painted bed of the river sprites: "River gaps" below); the bed shows through (openness ≈ 0.4, `sea::RIVER_OPENNESS`); a slow drifting shimmer, no waves (`iso::river_shade`). Waterfalls and river mouths (2702–2704): see "Rivers into the sea" below. Water-field flag bit 1 marks river pixels.
- Wave events and run-up physics (2026-10-17, owner: water line too uniform, no visible extra movement, "more randomness, physics behind the waves"): each surf crest is an event with its own relative height (`iso::wave_height`: sets of large waves via a slow envelope over the wave number, random per wave, varying smoothly along the coast); the surf clock drifts so periods are irregular (`iso::surf_time`, monotonic). Waves break where the depth falls below H / γ (breaker index γ = 0.78), so large waves break further out. Run-up follows Hunt's formula R = ξ·H with the Iribarren number ξ = tan β / √(H / L) (`iso::runup_height`; H = 6 `HEIGHT` units for the largest waves, gain 1.6, horizontal reach ≤ 2 tiles), using the beach slope per pixel (smooth terrain gradient, water-field flag bits 2–7). Rush-up time grows with wave height, the backwash is slower (gravity). Foam appears on impact, scaled by the wave's height. The earlier run-up was set in `HEIGHT` units only, which on steeper beaches moved the waterline by a fraction of a tile and was not visible. This is a parametric physical model per wave, not a fluid simulation.
- `gpu::tests::shader_is_valid_wgsl` validates the shader with naga, so WGSL errors fail the tests instead of the viewer.
- Coastal waves (revised 2026-10-17 after owner feedback "flat, like a light reflection, lines tracing the shoals"; causes: crests followed the shore distance and so traced every lobe and shoal, waves had no height profile, breaking ignored depth): swell from one direction (`Waves::swell_dir`, diagonal on screen), crest phase `along / 2.6 tiles + t / 3400 ms + bend` with two noise scales bending the crests. Each crest has a height profile (gentle back, rounded top, steep front) shaded as relief (front darker, top brighter). Waves grow from 12 to 4 `HEIGHT` units of depth, break where the depth falls below ≈ 4 (narrow foam line on the crest, short whitewater trail, broken into pieces by noise) and run on as weaker bores over the flats; swash runs up the beach below 1.5 units. Shallow water is tinted by depth (8 units). Mixing the shore distance into the phase (to turn crests towards each beach) was tried and dropped: it compressed the phase into bunches of thin lines at shoal edges.
- Waterline: the original's waterline follows its terrain triangles, so it is straight between tile corners and steps along tile edges where the height changes within a tile (owner: "at water level you never find straight lines", except at buildings). Enhanced water decides where water is from a smooth surface instead: a cubic B-spline through the corner heights (no overshoot) plus fixed value noise of ±2 `HEIGHT` units (`sea::smooth_height`, `Waves::shore_noise`), with a soft edge of ±0.35 units (`Waves::shore_edge`). Water may thus cover the lowest beach pixels or leave the shallowest floor dry (relative to the waterline at 16); buildings and other objects are drawn on top as before. The signed depth over that surface is stored per pixel (`WaterField::depth`, 1/4 units around 128) next to a flag for the original's waterline (`WaterField::flags`); the original mode uses only the flag.
- Deep water hides the sea floor: the floor fades into open water from 4 to 14 `HEIGHT` units below the waterline (`iso::deep_water`, over the smooth surface of the waterline). The terrain height is smooth across tiles, so this removes the tile-shaped edges between the original's floor textures (shallows, sand, deep sea) that showed as a stepped boundary between near-island water and deep sea (owner feedback 2026-10-17). The original mode keeps the original floor.
- Shallow water within 2.2 tiles of the shore is tinted towards turquoise (RGB 0.36, 0.74, 0.76, up to 30 %).
- Detail level: fine foam texture fades out with the zoom (`iso::wave_detail`, 1 at group 0, 0 at group 2), so nothing aliases into patterns.
- Shore distance: per island, a chamfer distance field (in tiles) from every height-grid corner at or above sea level, smoothed by two 3 × 3 box-blur passes (removes the octagonal kinks), interpolated per pixel and stored in 1/32 tiles (`sea::SHORE_SCALE`; 7.97 tiles = open sea).
- The original's surf sprites (`ANLAGEN` 2708) are not drawn in enhanced mode; its own surf replaces them (they showed as dark diamonds over the tinted shallows).
- Smooth animation: the sea cross-fades between consecutive sprite steps (the original jumps every 50 ms).
- Smooth surface: each sea pixel averages the 2 × 2 pattern pixels at its position (premultiplied alpha), so the sprite's 50 % checkerboard (`BSH_RGBWZ`), which showed as fine diagonal hatching on high-resolution displays, becomes a continuous surface; the floor still shows through at 50 %.
- Deterministic: a pure function of position and time (value noise from an integer hash), so `--png --time` is reproducible.
- Evaluation: the GPU evaluates it per pixel; the CPU path on a grid of 4 / 2 / 2 px (groups 0 / 1 / 2, `sea::SHADING_STEP`), interpolated per pixel, so foam edges differ slightly between the two.
- Not yet: spray above the water at impact, wave interaction with rocks and ships; shore distance across islands (each island's field ends at its rectangle).
- Tests: `iso::tests::wave_noise_is_deterministic_and_bounded`, `crates/app/tests/view.rs::view_png_enhanced_water_is_opt_in`; visual comparison with `bench_frame --check` dumps (`BENCH_DUMP`).

### Water field: empty cells (T1f, 2026-10-21)
The water field (`sea::water_field`) is evaluated per pixel at the pixel's tile position (x, y) (`sea::field_at`), about 90 ns at group 0, and was 35-49 % of a chunk build (`docs/perf/README.md`, "T1f item 1"). Large parts of an island provably get the **empty texel** (cover, shore, depth, flags all 0). Once per island (`IslandWater::classify_cells`, in `IslandWater::build`; the field depends on (x, y) only, not on the zoom group), each tile is marked in `IslandWater::empty_cell` (one byte per tile). `water_field` writes the empty texel for a pixel whose position lies inside the island (0 ≤ x < w, 0 ≤ y < h) in a marked tile, without evaluating it. The pixels are identical; this is a proof, not a tolerance.

A tile (tx, ty) is marked when **both** hold:
1. **No river level at the four corners** (tx, ty), (tx+1, ty), (tx, ty+1), (tx+1, ty+1) (clamped to the grid, as `river_level` reads them): all are NaN. Then `river_level` returns nothing for any (fx, fy) (no tap has weight), so `river_point` returns nothing and the river branch of `field_at` is never taken.
2. **No sea**, either
   - (a) the tile's 8 × 8 block has no sea (`sea_chunk` false). `field_at` then returns the empty texel through `!sea_chunk`, whatever the depth; or
   - (b) the lowest of the 16 corners (tx−1 … tx+2) × (ty−1 … ty+2) (clamped) that `smooth_height` reads is at least `kEmptyLandHeight` = kWaterline + kSlopeBand + 1.3 · shore_noise + 0.5 = 16 + 12 + 2.6 + 0.5 = 31.1. In that case:
     - **Spline:** the cubic B-spline weights are non-negative for t ∈ [0, 1) (u³/6, (3t³ − 6t² + 4)/6 ≥ 1/6, (−3t³ + 3t² + 3t + 1)/6 ≥ 1/6, t³/6) and sum to 1, so the spline is a convex combination of the 16 corners and at least their minimum. The float rounding of 16 products of values ≤ 255 is below 0.001.
     - **Noise:** `height_noise` = (n₁ − 0.5) · 2 · amp + (n₂ − 0.5) · 0.6 · amp, with `noise3` values in [0, 1]. `hash3` is in [0, 1), and the lerps with fade weights in [0, 1] stay inside the range of their inputs up to an ulp. So the noise is at least −1.3 · amp = −2.6.
     - **Result:** smooth ≥ 31.1 − 2.6 − 0.001 > 28, so sd = 16 − smooth < −12 = −kSlopeBand. No beach slope is computed (slope 0, run_max = 0.4).
     - **Not original water:** `terrain_height` is a convex combination of its tile's four corners, which are among the 16, so under ≥ 31 > 16.
     - `field_at` therefore returns the empty texel through `!original_water && sd ≤ −(edge + run_max)`.

Pixels outside the island grid, and every unmarked tile, are evaluated in full as before. **Tests:** `water field: every position in an empty cell gets the empty texel` (synthetic, in CI: a ridge through the waterline and the threshold, a river over high ground; it also compares `water_field` with `field_at` per pixel; removing condition 1 or lowering the threshold to the waterline makes it fail).

Other CI tests:
- `a tile is empty exactly when its 16 spline corners clear the threshold`: a plateau at 31 has no empty tile and one at 32 is all empty; one low corner unmarks exactly the 16 tiles that read it.
- `the synthetic scene's digest is the one before the T1f speedups`: `tests/water_field_fixture.hpp`, two islands, pixels outside the grids. The digest was recorded with the sources of 7479a2a and is checked with and without the cell classes.

The game-file test `water field: empty cells hold on every island` covers every island template and the 0200Single / 0201SingleAddOn scenarios: 458 files, 11.8 M tiles, 4.33 M empty, 108 M positions sampled once (now 9 per tile), all empty. The scene digests are unchanged. A complete removal of the per-pixel field from the CPU is T11 §10.1 (a GPU field pass).

### Bounded blur and chamfer (T1f item 2b, 2026-10-21)
The river stages of `Scene::water_field_from` (`apply_fall_masks`: three `blurred_alpha` calls; `blend_rivers_into_sea`: three two-pass chamfers) ran over the whole chunk rect even when the river sprites cover a small part of it (up to 21 ms of river stages on the worst chunks, `docs/perf/README.md` "T1f item 1"). Both now run on a window around what can change. **Pixels identical**: the proofs below, the golden digests of the ten scenarios (whole scenes with enhanced rivers) and `water field: islands one tile wide or high classify and evaluate like the rest`.

**Blur (`blurred_alpha`).** The result at p is a function of the alpha values in the Chebyshev ball of radius 2r around p: the box filter of radius r reads the clamped window k ∈ [x − r, x + r] of its line, two passes per direction give 2r in x and in y, and a clamped index k < 0 maps to 0, which lies in [x − 2r, x + 2r] again (k ≥ x − 2r and k < 0 give x − 2r < 0 ≤ x); the closing step (`close`) reads a 3 × 3 neighbourhood, so one pixel more. The sums are exact integers, so a pixel whose ball holds only zeros is exactly 0 and the output float `0 · norm` is 0.0F, what the unbounded version stores. The window is the bounding box of the non-zero alpha, grown by 2r (2r + 1 with the closing) and clipped to the canvas: exactly the reach of the output. At a window edge that is not the canvas edge, the input of every pass is zero (each pass adds r to the reach: the inputs of the last horizontal pass reach r from the box in x, those of the last vertical pass r in y, one more with the closing, all less than 2r), so the edge repeat of a line there repeats zeros, as the pixels beyond the window are zeros; the output pixels on the edge are nonzero and correct. One pixel less cuts a pixel of the output: the synthetic test shows it. At a canvas edge the window is cut where the canvas is cut and the repeat is the real one. Inside the window the arithmetic is the same operations in the same order on the same integers.

**Chamfer (`blend_rivers_into_sea`).** One step of the two-pass chamfer costs 1 or √2 and moves by at most one pixel per axis, so the value at p is the minimum over scan-admissible paths from a seed, each costing at least the Chebyshev distance it covers, summed in path order (the same float sums in any window that contains the path, in the same scan order, so ties between equal costs resolve the same way: `relax` updates only when strictly less). Hence a value below a bound B depends on pixels within Chebyshev distance B only, and inside a window that contains that ball it is the value of the full rect; outside it a window value is at least the full value (a subset of paths) and so also at least B. The consumers read the three chamfers only through comparisons with those bounds:
- `dist` / `near_cover` are read at river pixels only, and only below `reach` (`dist >= reach` skips the pixel). A seed farther than `reach` from every river pixel cannot matter.
- the seam test `to_river + to_sea > seam` acts only on a pixel with both terms ≤ `seam` (both are ≥ 0): its river seed is within `seam`, its sea seed within `seam` of it, so within 2 · `seam` of a river pixel. Where either term is above `seam` in the full rect it is above it in the window as well, the same branch.
- a pixel with `kSeamDepth` > 0 (static_assert) can be a seam seed only if it is a `dist` seed (`sd ≥ kSeamDepth` implies `sd > 0`), so the early return on "no sea" in the window leaves, in the full rect, only seeds beyond `reach` and `seam` of every river pixel, which change nothing.
The window is the bounding box of the river pixels (`flags & 2`) grown by max(ceil(reach) − 1, 2 · floor(seam)) and clipped to the rect (a chamfer value below `reach` covers at most ceil(reach) − 1 pixels per axis; the seam sums are inclusive, so floor(seam) each; the synthetic test puts the sea at exactly that distance and shows one pixel less changes the result); it contains every river pixel, every pixel the seam can change (within `seam` of a river pixel), and the balls the chamfers read for them. A pixel the seam turns into river has its `dist` read in the final loop: its value is at most its `to_sea`, which is at most `seam` (the seam seeds are `dist` seeds and the chamfer is the same one), so its ball lies within 2 · floor(`seam`) of the river box, inside the window. The final loop (`shore`, `cover` of river pixels, including the pixels the seam turned into river) runs over the window, which contains all of them. No tolerance is involved: the window changes which pixels are visited, never a value read at a visited pixel.

## Wave simulation (enhanced water, GPU)
Owner decision 2026-10-17: a real fluid simulation instead of parametric waves ("still looks too uniform"), built for bigger maps and robust multiplayer. Code: `crates/render/src/fluid.rs` (parameters, swell, window, CPU reference solver), `fluid.wgsl` (compute shader, same arithmetic), `gpu_fluid.rs` (host), sampled in `gpu.wgsl` (`fluid_sample`, `fluid_shade`).

- **Render-only.** Reads terrain, never game state; nothing reads it back. It is not part of the deterministic simulation and cannot affect lockstep multiplayer; frame rate and timing may differ per machine.
- **Scales with the map.** A camera-local window sized to the view (`FluidConfig::window_size`: view span × cells per tile + recentre and sponge margins, at most 2048²; 16 / 8 / 4 cells per tile at zoom groups 0 / 1 / 2, raised from 8 / 4 / 2 on 2026-10-17 for finer waves and shorelines; ≈ 1700² cells at 3840 × 2160, zoom 0), stored as a ring buffer (texel = world cell mod size); it recentres when the view moves 64 cells, and only the newly visible strips get depth and initial state (computed on all CPU cores). Cost is independent of map size and island count; the island lookup for depth is linear in the islands (`Scene::fluid_depth`; replace by a spatial index for very many islands).
- **Set up in the background (2026-10-19).** A window for a new zoom group or size (95–145 ms of CPU work: depth of about 10⁶ cells, initial swell state, 20 MB of texels) is no longer built inside the frame in interactive use (`GpuLimits::background_fluid`, set by `GpuLimits::interactive()`, which the viewer uses; the default and all tests keep the blocking mode). `FluidGpu::update` then starts a job thread that computes the cells straight into the texture byte layout, and uploads the result in slices of at most 2 ms / 16 MiB per frame (`upload_budget_ms`, `upload_bytes_per_frame`) into a second grid (reusing the textures of the window replaced when the size is the same); a recentre does the same for its strips. The window in use keeps simulating until the new one is complete, the shader uses the analytic waves where no window covers a pixel (`fluid_inside`), and a request for another group or size cancels the job in flight. The new window starts from the initial state at the time the job started (the simulation then catches up, at most 12 steps per frame). Result: no frame of the viewer waits for the window (`docs/perf/README.md`, 2026-10-19). Visible consequence, to be decided by the owner: for 0.1–0.4 s after a zoom change the coast shows the analytic enhanced waves instead of the simulation.
- **Model.** Shallow-water equations on a staggered grid (elevation η in `HEIGHT` units, velocity in tiles/s), symplectic Euler, `dt` = 1/120 s (stable for dx = 1/16 tile at 3 tiles/s), up to 12 steps per frame (skips ahead when behind). Wave speed √(g·D): shoaling, refraction, diffraction and reflection emerge. Gravity follows from 3 tiles/s at 16 units depth (≈ real gravity at the game's scale of 1 `HEIGHT` unit = 0.04 world units, 1 tile = 1 world unit; with the first, slower choice of 1.5 tiles/s swash flow was too slow to reach up the beach).
- **Wetting and drying.** Flux with the upwind total depth `η + h` (≥ 0); a face flows only where the higher surface lies above the higher bed; the surface never drops below the bed; swash water above the waterline seeps away (0.4 units/s) so films fall dry. The run-up is simulated: on screen a pixel is water where the surface interpolated from the wet cells lies above the pixel's own smooth terrain.
- **Breaking.** Where the still depth exceeds 3 units, elevation above 0.8 · h is dissipated (rate 8/s) into foam; shallower, the broken wave runs on as a bore and only friction slows it (clipping there stopped all run-up). Swash flow churns foam; foam drifts with the flow (semi-Lagrangian advection from the cell-centre velocity) and decays with τ = 1.6 s; on screen its texture churns (two noise scales evolving over time). Before advection the foam stood where waves keep breaking and read as a static white line (owner feedback 2026-10-17).
- **Incoming swell.** Deep water (depth 10 → 15 units) and a 32-cell sponge at the window border relax to a sum of 8 plane waves with seeded random directions around the full circle (main direction strongest), periods 2.6–4.6 s and amplitudes up to 1.2 units; their interference gives wave groups and an irregular sea, and every coast receives waves.
- **Measured** (CPU reference, synthetic plane beaches, 15 s after warm-up): local shoreline excursion range 0.6–1.1 tiles for beach slopes 0.7–3 units per tile; with the first parameters (slow waves, breaking down to 0.5 units, amplitude 0.35) it was 0.1–0.3 tiles, which the owner saw as "the water does not move".
- **Shading.** Relief lit from the screen's top left (subtle on the open sea, stronger in the surf), foam from the simulation, foam edge at the moving waterline, depth tint; small-scale noise for detail. Rivers keep `river_shade`; the CPU fallback (no GPU) and `--png` keep the parametric model (`iso::wave_shade`).
- **Tests.** `fluid::tests` (window strips, seeded swell, stability, breaking, run-up and backwash on a beach), `gpu_fluid::tests::gpu_matches_cpu_reference` (GPU vs CPU after 40 frames incl. a recentre, < 0.01; skipped without a GPU), WGSL validation of both shaders with naga.
- **C++ port** (2026-10-18, ADR 0001): `src/render/{include/anno/render/fluid.hpp,src/fluid.cpp}` (`anno::render::fluid`), same operation order as `fluid.rs`. `src/render/tests/fluid_test.cpp` repeats `fluid::tests` and the run of `cargo run --release -p anno-render --example digest_fluid` (synthetic beach and island, 300 steps, a ring-buffer recentre and fill, 300 more steps): six FNV-1a digests over the f32 bits equal the Rust ones bit for bit on the same C library — Apple macOS and glibc 2.39 (aarch64 and x86_64) have one table each, selected by the forcing digest, since `sin`/`cos`/`exp` round differently per libm (the two differ by ≤ 1.2·10⁻⁷ over the final state). MSVC's UCRT has a third table (measured 2026-10-18 on Windows 11 26H2, MSVC 19.44 and Rust 1.99.1 x86_64-pc-windows-msvc: C++ = Rust bit for bit, both differ from Apple and glibc from the forcing digest on). Elsewhere the swell and five cells are compared within 10⁻⁵ / 10⁻⁴. Deviation: `FluidConfig::window_size` returns `min(max(n, 64), size)` where Rust's `clamp` panics for `size < 64`. Not covered by the parity run (review 2026-10-18): `window_size`/`with_size`, recentres to the left or up, groups other than 0, the unforced interior (a 64-cell window is all sponge), non-power-of-two cell sizes.
- **Cost.** ≈ 1 ms per frame at 3840 × 2160 on the dev machine (`docs/perf/README.md`).

## River gaps (enhanced water; fixed 2026-10-19)
Owner report 2026-10-19 (own testing on the Windows PC, enhanced water, a jungle island): stretches of the painted riverbed showed brown bed and no water; in the original every river is connected end to end, because Anno 1503 has no partly dry riverbeds. A `fix`, not a taste question. The screenshot is `Islands/Dschungel/D_256x256_0045_5B.scp` at zoom group 1 (found by correlating the screenshot's blue pixels with renders of all jungle islands with rivers; the view is the 2494 × 1355 px window at scene pixel (-96, 1934), and the rebuild's render of that window matches the screenshot pixel for pixel in position, mean difference 2.7 of 255 per channel from the water animation).

**Measure** (`tools/river_qa.py`, `src/tools/river_qa/main.cpp`): the QA tool runs the viewer's own chunked calls (`Scene::ground_with_probe`, `Scene::water_field_from`), so it measures the field that the CPU path and the GPU compositor both draw; the GPU only shades it differently (checked below). Per scene and zoom group: O = pixels where the original draws river water (the river and waterfall/mouth sprites with the original's depth test; the sprites are a 50 % checkerboard, so O is closed over 3 × 3 pixels and stray single pixels at a bed's rim are ignored), W = pixels where enhanced water is drawn (field cover set and depth ≥ 0, i.e. alpha ≥ 0.5). **Gap** = O pixel with no W within `th/10 + 1` px (5 / 3 / 2 px at groups 0 / 1 / 2; closer misses are the two soft edges differing by a pixel). Connectivity: 8-connected components of O, and of W near O; an O component is **split** when it touches more than one water component and **lost** when it touches none.

**Root causes** (before the fix, 72 islands with rivers in the 5 climates that have them, 13 scenarios; Polar has no rivers):
1. *Wrong bed surface (dominant).* The enhanced river test compared the river level with `sea::smooth_height`, the cubic **B-spline** through the corner heights that the sea's waterline uses (right there: an approximating spline hides the tile steps). A B-spline does not pass through its control points. A river piece's height byte is its lowest corner (`D_256x256_0045_5B`: 152 of 184 pieces have z = the minimum of their 4 × 4 corners; 181 of 184 have a corner 16 above z, so the banks stand 16 units over the bed), the river surface is z + 9 (`kRiverLevel`), and the weights of the spline at a corner are 1/6, 2/3, 1/6 per axis, so the floor of a channel one corner wide is lifted by 16/3 = 5.3 units in a straight channel and by (1 − (2/3)²) · 16 = 8.9 units at a bend or dead end: the river depth (9), so no water depth was left at the thalweg and the soft edge (±0.35 units) cut it. Of the 6,418 gap pixels of this island at group 2 none lay where no river level existed (`IslandWater::river_level` nullopt) and none under sea water: every one had a level and a bed above it, 0–2 units above for 3,169, 2–4 for 2,968, 4–8 for 251, more than 8 for 20, and 10 with the level above the bed but outside the river branch's soft edge.
2. *Different coverage rules.* The original draws a river sprite pixel where the terrain seen there is at most the piece's own height byte + 10 units (`kRiverTolerance`, the triangulated terrain); enhanced compared a level averaged over overlapping pieces and blurred twice (piece heights differ by several units along a river) + 9 with the B-spline plus ±3 units of fixed noise, so even with a correct bed the two edges could not agree.
3. No cause on the GPU side: the compositor reads the same field; the rendered images of the owner's window have the same gap share on the CPU and the GPU (below).

**Fix** (`sea::river_bed_height`, `Scene::apply_fall_masks`; CPU and GPU alike because both read the field):
- The river bed is an interpolating **Catmull-Rom** surface through the corner heights (clamped to the four corners of the cell, so it never overshoots) plus half the shore noise (`kRiverBankNoise`), instead of the waterline spline. Banks stay organic (noise, soft edge) and the bed keeps its depth.
- The painted bed is a floor: the river pieces' own sprites, drawn with the original's depth test into a mask (`IslandData::river_sprites`), are closed over the checkerboard, blurred like the falls' shapes (≈ 4 px at group 0) and give the water depth `max(physical depth, (alpha − 0.5) · 4 units)` (`kBedEdge`, `kBedDepth`). So enhanced water never ends short of the original's water, even where a bed is only a few pixels wide where two pieces meet (these necks were 1–3 px hairlines with alpha 0.5 before); where the physical bed is deeper, the physical depth stays. Soft edges stay (the blur), original water is unchanged (sprites are drawn as before), nothing touches sim state.

|---|---|
| Scale | per axis `kTile[from] / kTile[to]` (width and height separately): 2 between groups 0 and 1, 2.1 between 1 and 2; scene pixels are linear in tile coordinates per group, so this keeps the world alignment (up to the rounding of the tile sizes) |
| Sampling | nearest neighbour at the pixel centre: source pixel `floor((2 p + 1) num / (2 den))`; `render::stand_in_source` (CPU reference) and `floor_div` in `gpu.wgsl` are the same integer rule |
| Source group | per part, not per chunk: `render::stand_in_cover` walks `render::stand_in_groups(group)` (nearest first, the finer group at equal distance); a part of the destination chunk whose source chunk is not on the GPU (CPU reference: in the cache) is split by the source chunks of the next group, and so on; parts of one source chunk that join are one draw. What no group covers stays open sea. The GPU and the CPU reference use the same function |
| Which chunks | visible chunks of the group shown that are not real on the GPU; O(visible missing x groups x chunks covered), at most `ceil(ratio) + 1` per axis |
| Drawing | one draw per source chunk (`render::stand_in_spans`: the exact part of the destination chunk that source chunk shows, so nothing is drawn twice) in the four chunk passes (terrain, ground, sea, objects), with a `Piece` uniform at a dynamic offset (group 2); the source chunk's own textures are bound, nothing is copied or converted. The pieces are written into one buffer that grows as needed |
| Kept | `FrameRenderer` keeps (does not evict) the cached chunks that would stand in for a visible chunk (only those already built) |

| Not done | (T1d/T1e added the cross-fade and the prebuilt neighbour groups, next section); the CPU viewer path draws open sea (the CPU reference exists, `FrameRenderer::stand_ins`, off by default, because per-frame resampling of ~5 MB per chunk is out of proportion for the fallback path) |

Tests (`gpu_test.cpp`): "stand-in spans tile the destination chunk and map by the tile ratio of kTile", "CPU reference: a missing chunk shows the scaled chunks of the nearest built group" (noise chunks, pixels within 1 of an independently computed source pixel, from group 2 and from group 0), "GPU stand-in chunks equal the CPU reference (synthetic)" (within 1 per channel, both source groups; off = no stand-in drawn). "stand-in cover chooses the source group per part" (all three target groups; a hole in the nearest group is covered by the next, the parts are disjoint and tile the chunk), "GPU stand-in with a hole in the nearest group equals the CPU reference, and the real chunk replaces it" (target groups 0, 1 and 2; the next frame draws no stand-in and equals the stand-ins-off frame). Mutations killed: a shifted pixel centre in the shader and in the CPU rule, a changed scale, the swap condition, the default switch, the tie order of the groups. The check that a source chunk on the GPU is real (`real`) cannot be killed: GPU chunks that are not real exist only for the visible keys of the current group and are dropped by `sync_chunks` when the group changes, so a source chunk of another group is always real (the check is a guard). Not covered by a pixel test: water objects in shallow water and the sea field cover of a stand-in (shader paths `sea_fs` with `chunk_local`, `object_in_water`); the PNG pair is the only evidence for those.

### Pan while zooming (T1d, 2026-10-20)

A stand-in needs a source chunk of another group **on the GPU**; a chunk takes 100-250 ms to build, so the content of a zoom step has to be ready before the step. `FrameRenderer::plan_margin` keeps built, nearest-first and behind the visible chunks: a margin around the view of one chunk plus, in the direction the view moves (smoothed velocity of the view centre), the distance covered in 2 x the measured build time + 0.1 s (`lookahead_rect`, at most `max_lookahead_chunks`); and the same for the view a zoom step would show in each neighbouring group (`adjacent_keys`). `GpuFrame` uploads those built chunks in frames where no visible chunk waits (`GpuLimits::prefetch_chunks`, `prefetch_per_frame`), the margin of the group shown first (`margin_keys`, T1e: a chunk entering the view on a plain pan is already on the GPU), then the neighbouring groups' views. A chunk replaces the placeholder an earlier frame drew for it (its stand-in or the open sea) by a dissolve (`chunk_fade_ms`, on a steady clock of the compositor, `GpuFrame::set_fade_clock`, not the animation clock, which pauses); a chunk that reaches the GPU in the frame it comes into view, and a rebuild of a real chunk, swap at once (T1e). The draw's piece record carries `transparent` (0 = opaque, so every older record is unchanged); the fading draws come last and use blending variants of the ground and sea pipelines (all other draws stay opaque), terrain switches at half, objects scale their alpha; the placeholder (kept for the fade) and the stand-in parts are drawn first, the real chunk over them. The eviction keeps a stand-in's sources while its chunk waits for the upload or dissolves (`FrameRenderer::shown_over_stand_in`). Because the ground pass and the sea pass both blend, a dissolve from open sea is an ease-in (about the square of the opacity); over a stand-in it is linear in the smoothstep of the time (tested at 1/4 and 1/2). Alignment: a stand-in is the source pixel containing the destination pixel's centre, a half source pixel off at an exact 2x ratio (a tie), tested on a smooth ramp world. Measurements: `docs/perf/README.md`, "T1d".

### Continuous zoom (T3 stages 1-2, 2026-10-21)

Owner proposal 2026-10-20: a slower, smoother zoom with a key back to the default, instead of three hard steps. Continuous is the viewer default on the GPU renderer (owner decision 2026-10-21, OQ-095 items 1-3: 1.1 per notch, 120 ms, `Home` / `0` back to group 1's width); `--zoom-mode stepped` is the faithful option. With the CPU renderer the default falls back to stepped silently; only an explicit `--zoom-mode continuous` prints "needs the GPU renderer; zooming in steps".

**Design: resample, not a native scale in every shader (deviation from the first sketch in `TASKS.md`).** The compositor works on one scene pixel per target pixel: the passes read their planes with `textureLoad` at `floor(pos.xy)`, the sea pattern, the wave window, the flow lattice, the sprites and the ships are all in the group's pixel grid, and the GPU = CPU tests pin that. A fractional scale inside them would touch every shader and lose those tests. So the picture is composed **exactly as before, on the scene grid of one zoom group**, into an offscreen texture, and **one extra pass** (`scale_fs` in `gpu.wgsl`, group 3, its own uniform `struct Scale`) resamples that grid onto the target (`GpuFrame::render(..., const Resample*)`). With no `Resample`, or the identity (scale 1, offset 0), nothing changes: no extra pass, no extra texture, all existing digests and uniform bytes untouched.

- `Resample`: `scale` (target pixels per grid pixel), `offset_x/y` (the target's top-left corner inside the composed grid: the fraction of the camera position the integer view origin dropped), `filter`. `resampled_view(cx, cy, out_w, out_h, scale, filter)` gives the integer grid rectangle (one pixel more than the far edge, for the filters' reach) and the `Resample`; the chunks, sprites and the wave window follow `view` as for any other view, so they cover the larger area at a scale below 1.
- Filters (`ResampleFilter`), all with `textureLoad` (the grid is an unfilterable float texture): `Nearest` (the pixel-art look; for a scale above 1), `Bilinear`, `Box` (the mean of ceil(1/scale)² samples over the output pixel's footprint, at most 8 x 8 = `kMaxBoxTaps`; for a scale below 1, where nearest would skip pixels and shimmer), and `Area` (the coverage-weighted mean of the grid pixels the output pixel's footprint, 1 / scale wide, overlaps: at most 2 x 2 for a scale of 1 and above, so every output pixel is equally crisp; exact below 1 as well, up to 8 pixels per axis). The viewer takes Box below 1 and **Bilinear from 1** (`resample_filter_for`; the owner at the fix 1 look: "bilinear works very well", OQ-095 item 5; nearest at a fractional factor such as 1.13 doubles every 7th-8th row and column, the "pixelated" look he first saw); `ANNO_VIEW_RESAMPLE=nearest|bilinear|box|area` forces one (the A/B; Area stays selectable and tested, GPU = CPU model). Area reads at most 8 x 8 grid pixels (the shader's loop limit, scale >= 1/7): below that the weights are renormalised (no darkening), and a forced Area below scale 1 becomes Box.
- Tests (`gpu_test.cpp`, synthetic, noise at every pixel): scale 2 nearest equals the pixel-doubled grid exactly; an offset of 0.5 grid pixels at scale 1 picks the pixel x + 1; scale 2 bilinear within 1 of a CPU bilinear; scale 0.5 box within 1 of the 2 x 2 mean of a grid composed at twice the size; area at 1.37, 1.13, 1.01, 0.63 and with unequal offsets within 1 of a CPU model of the shader (the footprint overlaps written out in `double`); an identity `Resample` renders the same bytes as none; `resampled_view` geometry. Mutations caught: offset dropped, nearest rounding, bilinear centre, box offset, box taps.

**The viewer** (`--zoom-mode continuous|stepped [--zoom-step f] [--zoom-ease ms]`): the state is the tile width in screen pixels shown (`zoom_now_`) and wanted (`zoom_target_`); the scale of the group shown is `zoom_now_ / kTile[group].w`. A wheel notch multiplies the wanted width by `--zoom-step` (default 1.1; a precision wheel's fractions too), `+` / `-` by its third power, `Home` / `0` back to group 1's own width (42). The shown width eases to the wanted one in the logarithm (equal notches look equally fast at every scale): the remaining distance shrinks by e^-3 (95 % covered) in `--zoom-ease` ms (default 120). The point under the cursor stays fixed: the camera moves by the anchor's offset from the window centre times the change of a screen pixel's size in scene pixels. The level composed on is chosen as **"Choosing the level"** below (stage 3 fix 1; stages 1-2 took the level nearest in ratio, which magnified the grid by up to 1.45 with the nearest filter); the camera is converted by the tile ratio as `Viewer::zoom` does. Range for now: half a group beyond the ends (tile width 14.1 .. 118.8; `kZoomEndFactor`); more zoom-out needs mips of the grid (stage 3). Panning (drag, keys) is in screen pixels, divided by the scale. The zoom maths (easing, anchor, group choice) is nno/app/zoom.hpp, tested without SDL; the group is chosen also at rest, so a group whose sea pattern was not ready is taken when it is. The grid is rounded up to a multiple of 64 pixels (kResampleGridStep) so the textures are not recreated every frame, the scale is limited to 1/64 .. 64 and raised when the grid would exceed max_grid (8192, the WebGPU minimum of maxTextureDimension2D): a very large window then zooms in slightly more than asked. The stepped mode and the CPU renderer are unchanged.

**Choosing the level (stage 3 fix 1, 2026-10-21).** The picture is composed on the **coarsest level whose tile width is at least the zoom**, i.e. the scale `zoom_now / tile_w(level)` is at most 1 and the resample pass reduces (Box), never magnifies. `zoom_level_for` (`zoom.hpp`): the finer level is taken **as soon as** the scale would exceed `max_upscale` (`--zoom-max-upscale`, default 1; 1.45 is the stage 3 look the owner saw), the coarser one only once the scale on it is at most 0.95 `max_upscale` (**5 % hysteresis on the coarse side only**: a resting zoom cannot flip). With the ratios 2, 2.1, 2, 2 ... between levels the scale of the composed grid lies in [0.95 / 2.1, 1] = [0.45, 1] below group 0, so the grid is at most 2.2 x the window per axis (4.9 x the pixels; it was at most 1.45 x), still O(window). The coarsest *ready* coarser level that fits is taken; **while none is ready the zoom is held** at `zoom_hold_floor`, 0.95 `max_upscale` x the next level's tile width, i.e. the scale on the current level stays at 0.475 (0.452 between groups 1 and 2) and the composed grid at most 2.2 x the window per axis, instead of growing without bound with the wheel (test "the zoom is held while the next coarser level is not ready"; zooming in is never held). A finer level that is not ready is bridged by the next coarser one that is, **magnified** (bilinear), the current level at the latest. The 8192 limit of the grid texture (`resampled_view` raises the scale to fit; with the hold, only a window wider than about 3700 pixels reaches it) is tested in "resampled_view: negative positions, fractions, stable size, limits". Above group 0's tile width (up to `kZoomEndFactor`, sqrt 2) magnifying cannot be avoided: bilinear there too.

*Switching between derived levels does not change the picture.* A level's chunk is the 2 x 2 box reduction of the finer level's chunks (`reduce_chunks_2x`), and the Box filter at scale 0.5 is the mean of the same 2 x 2 pixels, so over ground (and sea of an unchanged pattern) a frame composed on level k and reduced by 0.5 equals the frame composed on level k + 1 up to 8-bit rounding: **within 1 per channel** (test "derived levels: the box at scale 0.5 of a level equals the coarser level", GPU, adapters 0 and 1). It is not exact where an alpha-over differs: the objects plane is reduced before it is blended over the ground (alpha-over and the mean do not commute where alpha varies inside the 2 x 2 block), and the sea is shaded per level.

Known limits of stage 2: the velocity estimate of the margin (`track_velocity`) sees the view centre move when zooming at the cursor, so the margin may point the wrong way for a moment; the per-group look (wave detail, object bands, river lambda) changes at a group switch (a small step, at scale 0.69 / 1.45 either side).

### Continuous zoom, stage 3 design: derived content tiers (the composed grid stays O(window))

**Status 2026-10-21: design, not yet reviewed; no code.** Orchestrator condition (TASKS.md T3 stage 3): the composed grid must stay O(window) at every zoom. Stage 2 composes on one group's grid and resamples it, so the grid grows with 1 / scale^2 below group 2 (scale 0.3 at 2560 x 1440: 8533 px, over the 8192 cap, and the sea, fluid and chunk passes all run on it). Mips of the composed grid do not help (the passes still run on the big grid); the content must come at the resolution that is shown.

**Zoom levels as a list.** `kTile` (three entries) becomes the default of a `ZoomLevels` table (PLAN 0.1: the groups are data). A level has a tile size, a kind and, for a derived level, a source level and an integer factor:

| Level | Tile width | Kind | Content |
|---|---|---|---|
| 0, 1, 2 | 84, 42, 20 | Built | the original groups, built from the original files exactly as today |
| 3, 4, ... | 10, 5, 2.5, ... (`20 / 2^k`) | Derived | the previous level's chunks reduced 2x (level 3 = group 2 reduced, level 4 = level 3 reduced) |

From level 5 on the tile width is not an integer; it only enters the zoom maths (the geometric middle between two levels, the scale `tile_shown / tile_level`) and the stand-in ratio, never a pixel loop. The list is built per scene: derived levels are added until the scene fits the window at the last one (the minimum zoom, the default; `--min-zoom <tile width>` overrides it, the viewer never zooms out past it). One configurable bound, `max_derived_levels` (default 8: tile width 0.08 px, a 512 px chunk then spans 131,072 group-2 pixels, far beyond any map), with that reason. The level shown is chosen as today (nearest in ratio, hysteresis 5 %) over the whole list, so the resample scale stays within 0.69 .. 1.45 at **every** zoom and the grid within 1.45 x the window (2560 x 1440: at most 3712 x 2088; 3840 x 2160: 5568 x 3132, below the 8192 cap). That is the O(window) condition, with a test that sweeps the zoom from minimum to maximum and checks the grid size and the visible chunk count against the bound.

**What is derived, and how.** A derived chunk has the same `kChunk` = 512 px size as every chunk and covers 2 x 2 chunks of its source level, each reduced 2x into one quadrant (512 is divisible by 2^9, so a quadrant never straddles a chunk border: no seams, no blending between sources). The reduction is a box filter over 2 x 2 texels in integers, defined per plane by a CPU function (`reduce_chunk_2x`, the reference; the GPU pass equals it exactly):

| Plane | Rule |
|---|---|
| `terrain` (u16, `kNoTerrain` = no ground) | mean of the valid texels (round to nearest, ties up); `kNoTerrain` when none is valid |
| `ground` (0RGB) | mean over the texels whose terrain is valid (a coast texel keeps the ground colour, the water is blended in by `field` as at every group); no valid texel: 0 |
| `field` (cover, shore, depth, flags) | cover, shore, depth: mean. `flags`: bits 0 (original water) and 1 (river) are OR-ed; the slope in bits 2-7 is **not** OR-ed (the OR of two 6-bit numbers is not a slope) but averaged over the texels with cover > 0 (a mean, rounded to nearest, ties up). Why a mean over the water texels: the slope belongs to the water surface, so land texels must not dilute it, and a maximum would let one steep texel set the swash run-up of a whole coast pixel. The reference test has two different slopes (3 and 7 give 5, a maximum would give 7) and a land texel whose slope bits do not count |
| `objects` (straight RGBA) | mean of the premultiplied colour and of alpha, un-premultiplied again |
| `base`, `flow` | not derived: ships come from the frame's sprite pass; river flow is shown with the legacy look at derived levels (a river is one or two pixels wide at group 2 and the flow lattice is per group pixel). **What the compositor assumes without a `base` plane:** the object-in-water effect (enhanced water only: objects sink into the water, foam at the contact) is off for that chunk, so objects are drawn over the water as pictures, which is the original game's look; the shader already does this for any chunk whose `base` is empty (`chunk.flags` bit 4 clear, `object_in_water` is not reached). At tile width 10 and below the effect is a few pixels. The GPU = CPU test at a derived level contains rocks standing in enhanced water and compares the picture with the CPU reference, which has no base either |

A level-k chunk is a box reduction of a box reduction, not of the 2^k x 2^k block; the reference is defined recursively, so CPU and GPU agree bit for bit. Sprites drawn per frame (ships, soldiers) are drawn at a derived level from the group-2 frames by the sprite pass at scale `1 / 2^k`, nearest; they are few, and the owner judges whether they shimmer. The **sea pattern** of a derived level is the group-2 pattern's step images reduced the same way (the pattern is periodic: texels beyond the period wrap, and the period shrinks to `ceil(period / 2^k)`; I measure whether the group-2 period divides, and if not the tiling drifts by under a pixel per period, stated in the report). The waves at a derived level are the analytic coast waves only (no simulated window, hence no OQ-076 cross-fade there), because at tile width 10 and below a wave is under four pixels. These are simplifications outside the original game (it never zoomed out past group 2), so they belong to the QoL layer, not to the faithful core.

**Where it runs.** On the GPU, at upload. The source chunk (a built group-2 chunk from the CPU cache, or a derived chunk already on the GPU) is the input of a render pass (`reduce_fs` in `gpu.wgsl`, `textureLoad`, no filtering) that writes the 256 x 256 quadrant of the destination chunk's textures; the source's CPU planes are then free, and a derived chunk keeps no CPU copy. No CPU chunk build is added: group-2 chunks come from the same `ChunkWorkers`. A destination chunk is complete when its four quadrants are in (quadrants beyond the scene extent count as empty open sea); until then it is **not drawn** (never a chunk with holes, the T11 rule) and its stand-in is shown.

**Review conditions of 2026-10-21 (orchestrator), as built into this design.** (1) `field.flags`: see the table (bits OR-ed, slope averaged). (2) `base`: see the table. (3) **Resident deep levels:** a derived level whose whole-scene chunk count is at most `resident_level_chunks` (default 16; reason: rebuilding a chunk of level k from nothing needs 4^(k-2) group-2 chunks built on the CPU, up to the whole scene, 612 chunks for `Single_01`, seconds of all cores, while 16 chunks of 4.3 MB are 69 MB) is never evicted for the scene's lifetime, so the overview is instant after its first build. (4) **The first zoom-out is aliased:** until the coarser level exists, the stand-in for a missing derived chunk comes from the finer level shrunk by nearest, which aliases; "never aliased" holds only once the coarser level has been built. The fill time (E) from the last built level to a complete view is measured on one and on 16 threads in the README measurement commit. (5) The level-table refactor is its own commit with no behaviour change (`ZoomLevels`, `zoom_levels.hpp`): the stand-in ratios, the margin's group conversion, the compositor's tile uniforms and stand-in piece records, and the viewer's zoom maths read the table; the default table is the three original groups; scene content (Anlagen layouts, sea patterns, river lattices) stays per built group (`kTile`, `kGroups`). Answers recorded: river flow at derived levels uses the legacy look (accepted); the default minimum zoom is the scene fitting the window with `--min-zoom` as the floor (the owner decides on the build, OQ-095 item 4); the reduction is a plain box mean (accepted); if the group-2 sea period does not divide by 2^k the derived pattern's period is rounded up and the drift is stated.

**Cache key and lifetime.** `ChunkKey` is `(level, cx, cy)` with `level` the index in the list, so a derived chunk is cached, trimmed and prefetched by the existing machinery. Derived chunks are evictable like built ones (a source needed again is rebuilt: build cost, not a correctness issue); sources are not retained once reduced. Memory is bounded in chunks of the **shown** level: at most `(1.45 W / 512 + 2) (1.45 H / 512 + 2)` chunks are visible (56 at 2560 x 1440, 104 at 3840 x 2160, 4.3 MB each on the GPU), plus the margin ring; the existing byte budget of the cache applies unchanged.

**Stand-ins and prefetch.** A missing chunk shows the nearest built level in ratio (ties to the coarser one: blurry, never aliased), scaled by the tile ratio as `stand_in_spans` does today, extended to ratios other than 2. The viewer already builds the neighbour group; for a derived level the neighbour is the next coarser level (the cheapest, 1/4 of the chunks). Source jobs are queued in order of distance from the view centre and capped (`derive_sources_in_flight`, default twice the worker count; reason: a zoom-out to the minimum of `Single_01` needs its whole scene at group 2, 34 x 18 = 612 chunks, and the workers must not be flooded ahead of the chunks the picture needs), so the picture fills from the middle outwards. The margin (T1e) is planned in chunks of the shown level. Item (c) of the stage (the velocity estimate must not see the zoom's camera move) applies here unchanged.

**Cost to measure (E, in the commit that builds it, reported in `docs/perf/README.md`).** Time from "the zoom reaches the last built level" to "all visible derived chunks complete" for `Single_01` at 1280 x 800 and 2560 x 1440 on one and on 16 threads; the reduce pass per chunk (GPU timestamps) on the RTX 4090 and the Radeon iGPU; the VRAM at the minimum zoom; the frame p50 / p95 / p99 / max at the minimum zoom (the grid is window-sized now, so it must equal the group-2 numbers within noise). Acceptance: no busy frame above 8 ms while zooming from minimum to maximum and back with a pan.

**Tests.** (1) `reduce_chunk_2x` against hand-computed 2 x 2 cases per plane (valid/invalid terrain mix, flag OR, translucent premultiplied objects); mutations: mean over all texels instead of the valid ones, OR replaced by max, straight instead of premultiplied. (2) GPU reduce pass = CPU reference **exactly** on real group-2 chunks of the canyon island and `Single_24` (levels 3 and 4, so the recursion is covered). (3) The compositor at a derived level equals the CPU compositor over the same chunk planes within 1 per channel (the existing GPU = CPU tests, with the level as a parameter). (4) The O(window) sweep above. (5) A level-table test: nearest-in-ratio choice with hysteresis over the whole list, the minimum zoom for a scene that fits, `max_derived_levels` honoured. (6) Quadrant bookkeeping: a partial chunk is never drawn; an edge chunk with empty quadrants completes.

**Order in the code (each its own commit once this note is accepted):** the level table and the generalised zoom maths with the sweep test; `reduce_chunk_2x` with its tests; the GPU reduce pass and its exact test; derived chunks in the cache, stand-ins and prefetch; the derived sea pattern and the sprite scale; the README measurements. The items (a)-(h) of the stage 3 entry follow.

**Questions for the orchestrator / owner.** (1) Is river flow with the legacy look at derived levels acceptable (the flow lattice has no equivalent at tile width 10)? (2) The default minimum zoom "the scene fits the window" goes down to tile width 2.5 for `Single_01` at 2560 x 1440; `--min-zoom` sets a floor; is a higher default floor wanted? (3) The reduction is a plain box mean; a gamma-aware mean would keep dark sprites darker against light sea; I do not propose it unless the owner dislikes the result.

**Stage 3 as built (derived levels draw, 2026-10-21).** Deviations from the design above and what each level does:
- **Where the reduction runs (fix 2, 2026-10-21: from the cache).** The viewer's derived chunks are reduced **on the CPU workers**, not by the GPU pass at upload, **from the four chunks of the level above as the cache holds them** (`FrameRenderer::plan_jobs`, `ChunkJob`, `render_derived_chunk`): the cache keeps `shared_ptr<const Chunk>`, the planner hands a derived job the four children's pointers (no plane is copied; the window thread only moves a finished chunk into its shared owner), a missing child is a job of its own before its parent and goes into the cache as an ordinary chunk of its level (normal trim rules; kept while the parent waits), and a parent whose children are not all cached waits for the next frame. A chunk that stays cached is therefore built **once** (`FrameRenderer::chunk_builds`; test "a zoom-out sweep builds every chunk once while it stays cached", blocking and workers). The first stage 3 build instead rebuilt a level-k chunk from nothing (`render_chunk(scene, level, cx, cy)` still does, as the reference and `FrameRenderer::derive_from_cache = false`, the fill-time baseline): 4^(k-2) group-2 builds per chunk, shared with no neighbour, again for every level. Measured in `docs/perf/README.md` ("T3 stage 3 fix 2"). Reason: the cache, the upload path, the stand-ins, the dissolve and the CPU reference all stay unchanged (a derived chunk is an ordinary `Chunk` under the key `(level, cx, cy)`), the window thread does no extra work, and GPU = CPU holds by construction for the planes. (The cost of this first design was repeated lower-level builds: a level-k chunk cost 4^(k-2) group-2 builds and two chunks of one level shared nothing: fixed by building from the cache, above.) The GPU reduce pass (`GpuFrame::reduce_chunks_2x`, exact against the reference, tested on both GPUs) is kept for the follow-up that builds level k from level k-1 chunks that are already on the GPU.
- **Scene and levels.** `Scene::set_levels` (the viewer sets them in `main.cpp` before the scene is shared: derived levels until the scene fits a 640 x 360 window, or `--min-zoom`, at most `--max-derived-levels`, default 8). At a derived level `Scene::sea` is `SeaPattern::reduced` of the source level's pattern (a box mean, wrapping at the period; **measured: the group-2 period is 320 x 160, which halves exactly five times, so the pattern tiles without drift at levels 3 to 7**; from level 8 on the rounded-up period drifts by half a pixel per period), `Scene::bounds` is the source's rectangle halved and rounded outwards, and the sprite lists, units and water objects are empty (**ships and soldiers are not drawn at derived levels yet**: the sprite scale is a later commit).
- **Compositor.** The tile size, the lift (`ZoomLevels::lift_scaled`, the built ancestor's lift divided by the reduction), the river view and the stand-in ratios read the level table; no wave simulation (analytic coast waves only) and no flow lattice at derived levels (a derived chunk has none; rivers use the legacy look); the object-in-water effect is off without a `base` plane on both paths (condition 2). `shade_sea_flow` takes the level table.
- **Cache.** `FrameRenderer::resident_level_chunks` (default 16): a derived level whose whole scene is at most that many chunks is never trimmed.
- **Viewer.** The wheel zooms through the derived levels down to the scene fitting the actual window (`--min-zoom` overrides, never below the last level / sqrt 2); `Home` / `0` as before; the stepped zoom keeps the three groups. Until the coarser level's chunks exist, the stand-in comes from the finer level shrunk by nearest, i.e. aliased (review condition 4); this is what the first zoom-out looks like.
- **Tests.** A derived chunk equals the reduction of its children (two levels, canyon island); the CPU frame at level 3 has the mean colour of the reduced group-2 frame within 6/255; the resident rule on and off; exact stand-in spans across 7 levels (independent arithmetic); the zoom maths over derived levels (scale stays within 0.68 .. 1.46 over a long zoom-out); GPU = CPU at levels 3-5 on the canyon island and `Single_24`, original water max 3 (at most 1/10000 of the pixels above 2), enhanced water within 4 % of pixels above 2 (the built groups: 2 %; more coast per pixel at a far zoom), on the RTX 4090 (Vulkan, adapter 0) and the Radeon iGPU (Vulkan, adapter 1).

| Island rectangle | the rectangle of its tile diamonds (as `Canvas::for_island`) plus a margin above of 504 / 252 / 126 px in groups 0 / 1 / 2 | P: largest `anchor_y` of any `Anlagen.dat` frame (entry 1330); an anchor lies on a footprint centre at least half a tile below the top vertex. Must grow once elevation raises tiles (OQ-026 a) |
| Island order | by far corner `x + w + y + h`, then `x` (back to front) | simplification as for objects; only matters where sprites rise into a neighbour's rectangle (OQ-026 f) |
| Composition | each island is drawn into a temporary canvas covering only its overlap with the target region, then composited source-over (straight alpha) | implementation choice |
| Templates (`.scp`) | one island at world tile `(0, 0)` (head position 0) | P |
| Island links (`INSELLNK`) | a stand-in island at the link's position: a real template from the linked dummy's climate folder with the link's size (size checked after loading; no dummies, no `PIRAT` templates), candidates sorted by file name, pick = island number mod count; the dummy itself if there is none | D: the original picks randomly with its per-game seed from the same candidates (no dummies, no `PIRAT` templates; `docs/re/annoscene.md` §3–5); the viewer has no seed and picks deterministically, and does not apply the original's `INFO` and ore conditions yet. The dummies are flat grass squares without coast, so they are not drawn |
| Open sea | the sea surface covers the whole region, between islands too (see "Water") | approximation (OQ-026 b) |
| Ships | each `SCHIFF` of a scenario ([`sze.md`](../formats/sze.md), "Units") is drawn with sprite set 0 of its `FigurenHeader.dat` entry (sails furled), frame `attr mod n` of the zoom group; the frame anchor lands on the world point `(x, y)` projected like a tile top vertex and raised to the sea surface (`SEA_LEVEL`, as the sea sprites) | P: position and figure; D: `attr` is the starting facing in 16 steps (`docs/re/fire-and-ships.md` §3.3); frame = facing at the default view rotation is assumed (mapping not traced); visual: anchors sit on the waterline of the hull (OQ-023 f); the sea-surface height for ships is an approximation |
| Ship order | ships are drawn after all islands, back to front by `x + y`; the scene bounds include them | simplification; matters only where a ship overlaps an island's sprites (OQ-026 f) |
| Soldiers | each `SOLDAT` is drawn with sprite set 0 of its figure (8 standing frames), frame `attr mod 8`, its `SHADOW` frame first; the anchor lands on the world point raised to the terrain height there (the island's `HEIGHT` grid, interpolated over the tile's two triangles as the ground) | P: position, figure, sets; `attr` = facing is a hypothesis (OQ-027 d) |

| Player colours | figures of the 17 player-coloured types (soldiers, scouts, pack animals, donkeys, flags; 69 figure entries) get their owner's colour: every palette colour whose green dominates (`G² > trunc(1.5 (R² + B²))`) becomes the player colour scaled by its brightness, exactly as the original (`anno_assets::figure::recolour`); colours from the original's table of eight. Each player's colour is assigned as at a new single-player game start (`anno_assets::unit::start_colours`: the scenario's `HEAD` colour, else the game-start rule); only the colour the human would pick on the colour screen is a stand-in (lowest free colour) | D: `docs/re/annodisplay.md` §8, `docs/re/annogame.md`, `docs/re/annoscene.md` §9 |

Sizes measured with `anno1503 --view … --png`: `Single_01.sze` is 16,960 × 8,886 px at group 2 (15 islands, 69,256 objects drawn, 11,717 invisible, 0 failed) and 71,232 × 37,296 px at group 0, too large for one image. The window therefore renders the static layers lazily in chunks (`anno_render::frame`); `--png` refuses scenes above 4 GiB of RGBA.

## Fidelity (2026-10-17)
Every sprite the renderer draws must reach the screen with all of its original pixels. Checked at single-pixel level:

- **Decoding and blitting** (`crates/render/tests/sprite_fidelity.rs`, needs the game files): every frame of every `Anlagen.dat` and `FigurenHeader.dat` sprite set and shadow at zoom groups 0, 1, 2 is decoded and drawn with the renderer's blitter onto a transparent canvas; the result equals the decoded image pixel for pixel (shadows: the coverage mask in the shadow colour), and the image keeps every covered pixel of the RLE stream. Buildings: 9,506 frames per group, 78,213,833 / 19,955,171 / 4,948,688 covered pixels; figures: 241,808 frames per group, 145,609,961 / 39,471,049 / 9,570,884 pixels.
- **Rows past the frame width** (OQ-025): the original draws them right of the frame box. Building frames were decoded clipped to the width, which lost 868 / 587 / 240 pixels in 154 / 179 / 129 frames (groups 0 / 1 / 2; e.g. pioneer houses 507, 509, plantations 812–814, cobblestone street 2515). They are now kept (`figuren::decode_frame_extended`: the image is widened, anchor and rows unchanged); culling widens each frame box by `iso::OVERRUN_SLACK` = 16 px, the largest overrun (group 0; 9 in group 1, 4 in group 2), and the GPU sizes atlas sprites by the image. Figures have no overruns.
- **GPU vs CPU** (`bench_frame --renderer gpu --check`, `Single_24.sze`, 1920 × 1080): at groups 0, 1 and 2, no pixel of the GPU frame differs from the CPU frame by more than 1 per channel (blending rounding); all texture reads are exact `textureLoad`s, no filtering or scaling.
- **C++ GPU compositor** (2026-10-18, wgpu-native, `src/render/src/gpu.cpp`, `gpu_fluid.cpp`): `src/render/tests/gpu_test.cpp` (needs a GPU and the game files; skips otherwise, fails with `ANNO_REQUIRE_GPU` set) renders the 18 frame-digest views of `Single_01` and `Single_24` with ships and soldiers on the GPU: original water within 1 per channel of the CPU path, enhanced water animates (the GPU uses the wave simulation, the CPU path the parametric model, so they are not compared), Single_24 draws 396 sprites, no GPU errors. A second case forces atlas growth (256² layers), read-back row padding (1001 × 601) and uploads spread over several frames: also within 1. The frame uniform's bytes are checked against `struct Frame` in `gpu.wgsl`. The GPU wave solver stays within 2.2·10⁻⁶ of the C++ CPU reference (`FluidGrid`) after 40 frames with a recentre. Against the Rust compositor: with the wave simulation off, the C++ GPU images of these views and of `bench_frame --check` (`Single_01`, 1280 × 720, all groups and styles) are byte-identical to the Rust GPU images on the same machine; with it on, `Single_24` group 2 at 900 ms gives the same difference to the CPU path (max 134, 123,547 pixels > 2) as the Rust compositor. Second review (2026-10-18), mutation testing with 83 small semantic changes of `gpu.cpp` and `gpu_fluid.cpp`: the first test set killed 48. Tests added from the review's candidates: enhanced water without the simulation within 2 % of the CPU path's pixels (the rest are coastline swash, where the GPU and CPU shading differ in Rust too: up to 1.1 % of pixels, max 89, on `Single_24`; not localised), the simulation visible on screen, solver time stepping (skip-ahead, time going back, group change), a resized 100-cell window, atlas growth read back across groups, stand-ins replaced over frames, invalid copies and frames counted instead of aborting, destruction with work in flight, and the device error counter after its owners are gone. With them 67 of the 83 are killed; of the 16 survivors 8 are equivalent or harmless (e.g. a clear colour the sea always covers) and the rest need counters or a synthetic scene (shadowed and translucent water sprites never reach the GPU sprite path in the `0200Single` corpus). The GPU tests also run on Linux (Docker, Mesa llvmpipe; CI's Linux runners use it through GL): with Vulkan all 18 cases passed at once; with wgpu's GL backend three things were wrong and are fixed (2026-10-18): (1) `%` on negative operands in the shaders (`wrapi`, `wrap`): WGSL defines it, but GLSL leaves it undefined, and llvmpipe got the wave window wrong for every size but powers of two (and the sea pattern on negative coordinates); both now use non-negative operands only; (2) a 1-layer texture bound as `texture_2d_array` is created as a plain 2D texture on GL: array textures (atlas, sea patterns, the dummy) get at least 2 layers; (3) the above-water sprites are bound at their buffer offset instead of drawn with a first instance (base-instance support may be missing on GL). (1) is in the shared shaders, so the Rust reference has it too; (2) and (3) remain in `gpu.rs` (no new work on the Rust code).
- **C++ port = Rust reference** (2026-10-18, ADR 0001): `src/render/tests/render_corpus_test.cpp` renders all ten `0200Single` scenarios and `Islands/Nord/N_064x064_0001_0B.scp` with every layer, ships and soldiers — the whole scene at group 2 (original water at 0 ms, enhanced at 2,500 ms) and a 1600 × 900 region at group 1 (both styles at 700 ms) — and 18 frames of the chunked frame pipeline (`FrameRenderer`, groups 0–2, `Single_01`, `Single_24`); every FNV-1a digest equals the Rust renderer's (printed by `cargo run --release -p anno-render --example digest_scene -- <game_dir> scenes|frames`), so the C++ output is identical bit for bit. Per C library (2026-10-18, Windows 11 26H2, RTX 4090): on MSVC's UCRT one line differs from the Apple/glibc table, `Single_16` group 2 enhanced (`b744196e…` instead of `98c476dc…`), because the enhanced water's `std::exp`/`std::pow` (`iso.cpp`) round differently in the last bit there; the Rust reference prints the same line on that machine, so C++ = Rust holds per libm, and the test keeps a short UCRT override list (`kUcrt`). Every original-water line and every other enhanced line is identical on all three. **Fallback (owner decision 2026-10-18: per-libm tables first, this only if they stop being practical):** replace `exp`/`pow` in the enhanced water by libm-free implementations, making enhanced renders bit-identical on every platform; that changes the enhanced digests everywhere and the Rust reference would need the same change. `src/render/tests/sprite_fidelity_test.cpp` repeats the decoding/blitting counts above. The C++ `anno1503 --png` gives the same pixels as the Rust one, checked by hand on 2026-10-18 (SHA-256 of the decoded RGBA, equal for both): `Single_01.sze --group 0 --at 100,100 --size 1200x700` `17510bba…6112f841`; `Single_01.sze --group 1 --at 120,90 --water enhanced --time 1500` `aea98724…49d264b7`; `0010SingleEndlos/01_1024_easy_256.sze --group 2 --at 500,500` (27 linked islands drawn as stand-ins; 5 islands in the view) `5f2c3243…9475142a`; `Islands/Polar/Po_064x064_0008_Eskimo.scp --group 2 --time 400` `87ea625c…357919a9`. Not an automated test. Float rules that make this hold: `-ffp-contract=off` / `/fp:strict`, float operations in the same order, and saturating float-to-integer casts with NaN → 0, NaN-ignoring min/max (`anno/render/numeric.hpp`).
- **Visual** (`--png --at … --size …`, magnified 5–10× with nearest-neighbour scaling): soldiers, cannons and ships at groups 0, 1, 2 keep weapons, helmets, rigging and wheel spokes; at group 2 details are single pixels and survive.

Not covered yet: comparison against captures of the original game (PLAN §0.4 (2), needs an x86 host). The original's 16-bit colour quantisation is deliberately not reproduced: the 24-bit palette colours are the reference (owner decision 2026-10-17, OQ-030). Player colours: rule and colours as the original (above); at group 2 the markers are single pixels and still show each army's colour.
